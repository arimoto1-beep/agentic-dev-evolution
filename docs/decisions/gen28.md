代わりに、資料そのものに 3 つの問題が出ました。いずれも **用途と関係なく前からあったもの** です。

## 判断

**3 つとも直しました。**「書いたとおりの資料が、どの道具で開いても同じように出る」ことを
この環境の前提として揃えるためです。3 つは別々の症状ですが、**同じ形の間違い** でした ——
**見た目の決定を、資料を開く側に任せていた** ことです。

### 1. 縮小を、指示ではなく実際の文字の大きさにした

はみ出したときは `a:normAutofit` の `fontScale`(「この枠の文字は 87.5% で表示する」)を
書いていました。**PowerPoint は守り、LibreOffice は読み飛ばします。** 実物で確かめました
(50% を指定した枠と 100% の枠が、同じ大きさで描かれます)。

この環境はスライド画像も動画も LibreOffice を通すので、**資料では収まっているのに、
そこから作る画像でははみ出す** ことになります。厄介なのは、どちらが本当かが
**両方を開いて見比べるまで分からない** ことです。画像を見て「崩れている」と判断して
シナリオを直すと、資料のほうを壊します。

そこで縮小率を書くのをやめ、**run の文字の大きさそのものを書き換えました**。
`normAutofit` 自体は残します(縮小率は付けません)。あとから PowerPoint で文字を
足したときだけ、そこから先を PowerPoint に任せます。

この指示は 3 か所で使われていました。本文の高さ・コードの幅・**スライドの見出しの幅** です。
つまり **長い見出しがスライドからはみ出すのも、ずっと直っていませんでした。**

### 2. ひな型が持っている文字の変換を打ち消した

章扉は python-pptx の既定のひな型の `Section Header` を使っていて、その見出しは
`cap="all"` を持っています。**これは LibreOffice の癖ではなく、PowerPoint でも
同じように大文字になります。** 資料の中身は正しいので、成果物を目で見るまで分かりません。

run に `cap="none"` を書きました。書く場所は `set_run_fonts` です
(見出し・本文・コード・図解・表・フッタの run が全部ここを通ります)。
フォントを run 自身に書いているのと同じ理由で、**見え方をひな型に委ねない** ようにします。

### 3. 図解も、図と同じく場所を譲るようにした

`renderer` は図解を box の高さに合わせて縮めています(「図が下の中身に重なるより、
小さく出るほうがよい」)。ところが `layout` は図解を「縮められないもの」として数えていて、
**代わりに文章が縮み、それでも入りきらずに帯へはみ出していました。**
`flexible` の判定に `KIND_DIAGRAM` を足しました(定数も `MIN_IMAGE_SHARE` ->
`MIN_FIGURE_SHARE`)。

これは gen27 の「次の Run への提案 1」で名指しされていた場所そのものです。
中身の種類を足すときに触る 7 か所のうち、**`layout` の見積りと `renderer` の実際が
一致すること** は忘れても何も言われない、と書かれていました。実際に食い違っていました。

### 採らなかった案

1. **シナリオ側だけ直して終わりにする。** 3 枚の警告は、書き方を変えれば消えます。
   実際に消しました(下記)。ただし **1 と 2 は「警告が出ない場面でも起きる」** ものです。
   見出しの縮小は警告を出しませんし、大文字化は警告の対象ですらありません。
   シナリオを直しても、次に同じ資料を作る人が同じところで転びます。
2. **等幅・レイアウトの前提を LibreOffice 側で合わせる。** gen27 がフォントで同じ道を
   試して失敗しています。**その環境にその設定がある場合だけ揃う** 作りが増えるだけです。
3. **勉強会用のレイアウトや設定(時間配分・章ごとの持ち時間)を足す。** 見送りました(下記)。
4. **動画も作る。** 作りませんでした(下記)。

### シナリオ側で決めたこと(環境の話ではありません)

長いコードをどう見せるかは、環境ではなく資料の作り方の問題です。元記事の Python は
215 行あり、1 枚には載りません。**関数の一覧(表)を 1 枚置いてから、要点を 3 枚に
抜き出しました**(完了待ち / 実行開始 / 証跡保存と判定)。全量は載せず、
「手元で全体を見たい方は元の記事を」と発表者ノートに書いています。
元記事の ASCII 罫線のディレクトリ図(`├─`)は、罫線を使わない字下げに直しました
(gen27 が消したはずの前提を、こちらから持ち込まないためです)。

## 検証

1. **症状が本当に出るか。** 直す前に、それぞれ実物で確かめました。

   | 見たもの | 結果 |
   | --- | --- |
   | `fontScale=50%` と `100%` の枠を並べた .pptx を画像にする | **同じ大きさで描かれた**(LibreOffice は読み飛ばす) |
   | 生成した資料の 9 枚目の XML | `normAutofit fontScale="87548"` が書かれている。それでも画像では本文がページ番号に重なる |
   | 章扉の XML と画像 | 資料は `おまけ: 試験Runnerを作るなら`、画像は `試験RUNNERを作るなら`。原因は `Section Header` レイアウトの `cap="all"` |

2. **直ったか。** 同じ 3 つを作り直して目で確認しました。50% が半分の大きさで描かれること、
   本文が帯に重ならないこと、`Runner` が `Runner` のまま出ること。

3. **テストが落ちるべきときに落ちるか。** 通ることだけを見ても、何も守っていないテストと
   区別が付きません。3 つの修正をそれぞれ元に戻して確かめました。

   | 戻したもの | 結果 |
   | --- | --- |
   | 縮小を `fontScale` の指示に戻す | `tests/test_shrink_text.py` の **10 件中 8 件** が落ちる(残る 2 件は仕組みに依存しない「下限で止める」「縮める必要が無ければ縮めない」) |
   | `cap="none"` を書かない | `tests/test_theme.py` の 1 件が落ちる。**守っている相手が実在すること**(レイアウトに `cap="all"` があること)を確かめるテストを別に置いた |
   | 図解を「縮められないもの」に戻す | `tests/test_layout.py` の新しい 3 件が落ちる |

   3 つ目は、最初に書いたテストが **戻しても通りました**。「図解が縮む」だけでは、
   全体が一律に縮む場合と区別できません。「**譲るのは図解であって文章ではない**」まで
   書いて、初めて落ちるようになりました。

4. **既存を壊していないか。** `-m "not slow"` が 756 passed(この Run の前は 741。
   増えた 15 件は今回のもの)。

5. **資料を最後まで作ったか。** 44 枚 / 1920x1080 の画像 44 枚 / 発表者ノート 44 枚
   (6,403 字、空のノート無し)。**44 枚すべてを画像にして目で見ました**(4x6 の一覧に
   まとめたものと、図解・表・コード・引用・章扉・表紙は原寸で)。
   シナリオを直したのは 3 枚で、いずれも「図の下の文章を上へ移す / 1 文にまとめる」です。
   最後に残る警告は 1 件(25 枚目の図解が 7 項目)で、これは読めることを確かめたうえで
   残しています。

## 次の Run への提案

指示ではありません。現在の状態を見て、評価し直してください。

1. **「資料と、そこから作る画像が同じに見えるか」を、通しで確かめる手立てがありません。**
   今回の 3 つは全部この形でした ——資料の中身は正しく、出てくる絵だけが違う。
   気付けたのは、**44 枚を全部画像にして目で見たから** です。目で見る以外の方法は
   まだありません。ただし **自動で判定できる形にするのは難しい** と考えます(何が
   「正しい絵」かを決められないため)。**当面は「作ったら全部画像にして見る」を
   手順として続けるのが現実的** で、そのために今回 4x6 の一覧を作りました
   (その場限りのスクリプトです。仕組みとしては残していません)。
   繰り返し要ると分かったら、そのとき `note2slides-images` の隣に置くのがよいと思います。
2. **同じ形の資料をもう 1 本作ると、時間の見積りが要るかどうかが分かります。**
   今回 44 枚を作って、「これは何分の発表になるのか」が最後まで分かりませんでした。
   困りはしましたが、**1 回では、それが今回だけの事情かどうか判断できません**。
   もう 1 本作って同じところで困ったら、そのときに足すのがよいと考えます
   (ナレーションの文字から読み上げ時間を見積もる形が素直です)。
3. **ひな型のレイアウトが持っている指定は、`cap` だけとは限りません。**
   今回は大文字化を打ち消しましたが、同じ場所には行間・字間・色の既定も入っています。
   **全部を先回りして打ち消すのは、症状が出ていないものを直すことになる** ので
   やめました(gen26 / gen27 と同じ理由)。次に「書いたとおりに出ない」ものを
   見つけたら、`set_run_fonts` に 1 行足すのが同じ直し方になります。
