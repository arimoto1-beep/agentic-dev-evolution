## 判断

問題を「記録する習慣が無かったこと」ではなく、**「判断を置く場所が無かったこと」** と捉えました。
根拠は上の 2 つの観察です。理由を残す書き方は README にも `NOT_CHOSEN` にも実際にあるのに、
見送りの記録だけが 1 件も無い。書く気が無かったとは考えにくい。
ただし README は「使う人に向けて、今どうなっているかを説明する」
文書で、改善の優先順位や見送りはその主題に入りません。置く場所が無ければ書かれません。

そこで、次の 3 つをまとめて入れました。1 つでも欠けると効かないと判断したためです。

| 入れたもの | 無いとどうなるか |
| --- | --- |
| `docs/decisions/` に Run ごとの追記型の記録 | 判断の置き場所が無い |
| `AGENTS.md` からの参照と、読み書きの手順 | 書かれても見つからない(AI が自動で読むのは `CLAUDE.md` -> `AGENTS.md` だけ) |
| `tests/test_decision_log.py` で形を固定 | 数 Run で書式が崩れ、読む側が毎回全文を読むことになる |

記録の粒度は「判断だけ」に絞りました。前回の Run で、実装状態はコード・README・Git 履歴から
かなり復元できることが確認されています。復元できるものを書き写すと、更新されないまま古くなり、
**次の Run に嘘を伝えます。**

### 採らなかった案

1. **README に節を足す。** 既に 1376 行あり、しかも README は現在の状態を書く文書です。
   過去の判断を混ぜると、使う人には不要な記述が増え、読む側は「今の説明」と「当時の判断」を
   区別しながら読むことになります。
2. **コミット本文とタグ注釈に書く。** 場所としては正しく、gen7 の実績もあります。採らなかったのは、
   (a) 見送りや次の候補は特定のコミットに属さない、(b) 履歴は書き換えないので、後の Run が
   「その判断は今も有効か」を更新できない、(c) 一覧できない、の 3 点です。
   ただし **併用します**。実装の理由は今後もコミット本文が適切です(この記録では繰り返しません)。
3. **機械可読な形式(JSON / YAML)と CLI。** 判断の理由は文章でしか書けません。項目を固定すると
   書ける内容が痩せます。読むのは人と AI で、集計する予定はありません。Markdown のままにしました。
4. **過去の Run の判断を推測で埋める。** 事実と推測が混ざると、次の Run が推測を根拠に判断します。
   別ファイルに分け、「事実」「分からないこと」「根拠付きの推測」を分けて書きました。

### 「そのまま実行させない」ために決めたこと

この記録は、次の AI に作業を指示するためのものではありません。評価し直せることを優先して、
次のようにしました。

* 各記録は **「この Run が見た状態」から始めます。** 判断そのものより、判断の前提を先に見せます。
  前提が今と違っていれば、結論を読む前に疑えます。
* 「見送り」には理由だけでなく **見直す条件** を書きます。見送りが永久の決定にならないようにするためです。
* **「過去の判断の再評価」を必須の見出しにしました。** 評価し直す行為を例外ではなく手順にします。
  結果として、次の Run は直近の記録を読まなければ自分の記録を書けません。
* 過去の記録は書き換えません。変わったことは一覧の「その後」でたどります。
  当時どう考えていたかが消えると、比べられなくなるためです。
