## この Run が見た状態

人が gen39b の動画を部分的に見て、3 点を指摘した。2:41 - 3:06 のノッキングがプレイグニッションと混同している可能性、
7:02 - 7:45 の比べる場面で遅閉じ・隙間・膨張比・「同じ強さ」「使い切る」が混同している可能性、7:45 付近で字幕と下部のラベルが重なること。
あわせて、人の確認が大きなボトルネックになっているので、まとまりごとに短く確かめられる形を、と求められた。

調べて分かったこと:

* **2 つの指摘はどちらも当たっていた。** ノッキングは点火のあとの現象で、gen39b の言い方と絵(火花なしで燃え出す)は点火前の着火を描いていた。
  比べる場面は、押し縮めたあとの圧力を「空気の量」で説明していた。
* **同じ誤りが、指摘の外にも残っていた。** gen39 から使っているエンジンの絵は、アトキンソン側も普通と同じ隙間で描いていた。
  絵の寸法から計算すると、実効圧縮比 5.1(普通 7.2)・膨張比 7.2(普通と同じ)で、「圧縮が弱いだけ」を描いていた。押す力の矢印には、
  gen39b が却下したはずの「空気が少ないぶん弱い」が残っていた。gen39b は「数画素の差で見えない」と見送ったが、見えないのは差の大きさではなく、
  **絵が間違った関係を描いていること**だった。
* **字幕の重なりは、再生環境だけの問題ではなかった。** 動画には字幕が入っていない。ffmpeg(libass)の既定の描き方で SRT を重ねると、
  名前に重なることを再現できた。全 41 場面のうち 37 場面が、字幕の出る帯(下 15% ほど)に札・結論・名前を置いている。
* 人の確認の単位として、既存の **章(8 個、46 秒 - 2 分 28 秒)** がそのまま使えた。章は場面の境目で始まるので、文の途中で切れない。

## 判断

### 1. 説明は「資料にあるか」で直し、言えない所は言わない

ノッキングは Wikipedia(日・英)と Motor-Fan の技術者インタビュー、隙間は Honda Fit(2013)のファクトブック(「13.5という高圧縮比」)と
Wikipedia の Miller / Atkinson cycle で確かめてから直した。該当文は `build/gen39c/refs/FACTS_gen39c.md`。

* ノッキングの説明は、資料の筋(点火 → 燃え広がる → 届く前の端の混合気が高温・高圧で自己着火 → 圧力の波)をそのまま初学者の言葉にした。
  「デトネーション」「エンドガス」「オクタン価」は使わない。新しい語は増やしていない。
* 比べる場面の鍵の語を「強さ」から「押し縮める割合」に変えた。17 枚目で定義した圧縮比の言い換え(「どれだけ小さく押し縮めるか」)と同じ語で、
  新しい語ではない。「何分の一」は「ナンプンノイチ」と読まれたこともあり、使わなかった。
* **普通と比べた実機の圧縮比の数字は出さない。** 同じ資料で並べた一次資料を読めていない(トヨタの 13.0 は二次資料)。
* 採らなかった案: 21b だけを直す。エンジンの絵が誤った関係を描いたままだと、15 - 21 枚目で見た絵と 21b の説明が食い違う。
  隙間を変えるのは部品(`parts.py`)の 1 か所で済み、普通のエンジンだけの場面は 1 画素も変わらないことを確かめられた。

### 2. 字幕は、公開用の動画では決めずに人に渡した

直した場面(21b)の名前は上へ移したが、残り 36 場面の下部は動かしていない。全場面を縮めて余白を作る案と、場面ごとに動かす案があるが、
どちらも全場面の見た目を変える。「既存の成果を維持しながら」という指示と、見た目の価値判断が絡むので、選択肢と勧めを書いて人に渡した。
確認用のクリップでは、字幕を絵の外の帯に出すので重ならない。README に「下 15% に隠れて困るものを置かない」を書いた。

### 3. 人の確認の単位を「章」にし、道具にした(`tools/review_pack.py`)

確認のボトルネックは、14 分を通して見ること自体と、止めると再開しにくいことだと考えた。新しい区切りを作らず、既存の章を使った。

* 章の前後に、隣の章の 1 文を付ける。字幕の切れ目で文末まで延ばすので、文の途中から始まらない。帯に「確認対象外」と出す。
* 字幕は絵の下の帯に焼き込む。確認する人がナレーションの文字を読みながら見られ、重なりも起きない。
* `index.html` に判定・メモ・再生位置を残す(ブラウザの localStorage)。「続きから」で最初の未確認の章へ戻る。メモは Markdown にまとめてコピーできる。
  サーバも外部の読み込みも要らない。
* 変えた場面とその確認点を JSON で渡すと、章に「変更」の印が付く。変えていない章は流れだけ見れば済む。
* **道具にした理由:** gen34-2・gen39・gen39b・gen39c と、人のレビューが 4 回続いた。毎回同じ形で要るので、この Run のスクリプトではなく `tools/` に置いた。
  採らなかった案: 場面ごと(41 本)に切る。短すぎて流れが判断できず、本数が多いと再開の目印にならない。

### 4. 確かめる順序

書き出しは 3 回。1 回目は `motion_check` が 21b の動きの引き伸ばし(1.59 倍)を見つけた。2 回目は、完成した mp4 から段ごとに抜いたコマで、
上へ移した名前に空気の矢印が重なっているのを見つけた。どちらも、絵の素材だけを見ていたら見落としていた。

## 見送り

* **公開用の動画の字幕の帯。** 判断 2。人が選んだら、(b) なら書き出し 1 回、(c) なら 36 場面の描き直し。
* **22 枚目の熱の行き先の棒(32% / 40%)。** 40% が Honda の最大熱効率(他の技術も含む)を思わせるが、今回の指摘の外。人が気にしたら直す。
* **「並べて」の発音。** 音声認識が「舐めて」「なべて」と書き起こした。読みの指定は合っているので、聞かずに直すと別の崩れを入れるおそれがある。人に聞いてもらう。
* **確認ページを実際のブラウザで開くこと。** この Run では DOM を模した簡易環境で処理を動かしただけ。人が最初に開いたときに崩れていたら直す。
* **説明の筋を点検する道具。** gen39b の見送りを維持。今回の誤りは「疑問の鎖」では見つからない種類(答えている場面はあったが、答えが誤っていた)で、
  必要だったのは資料との照合だった。道具より、場面ごとに「根拠の文」を持つ書き方のほうが効くかもしれないが、1 回では決めない。

## 検証

**動画を再生して通しで見ていない。音を聞いていない。** 手順と結果は `build/gen39c/README.md` の「確かめたこと」。要点だけ書く。

1. 改善前を保存した(未コミットのコード差分・未追跡ファイル・Gen39/Gen39b の 51,249 ファイルの sha1・元記事の sha1)。
2. 資料を読んだ。Web ページは取得用の補助エージェントに該当文を引用させ、Honda の PDF は直接読んだ。
3. 台本と絵の書き換えは `build/gen39c/scripts/patch_scenario.py` `patch_figures.py` にまとめた。
4. 読みを合成前に見た(「何分の一」を言い換え、調子の合図を 1 か所直した)。
5. 書き出し 3 回。すべて終わるまで待った。
6. 完成した mp4: 復号の誤り 0、27,190 コマ。変えなかった 37 場面は長さが gen39b と一致し、完成動画どうしで 99 コマを比べて違いなし。合図 89/89。
   繰り返しの継ぎ目の飛び 0、引き伸ばし最大 1.08 倍。
7. 変えた 7 場面を、完成した mp4 から段ごとに 3 コマずつ抜いて見た。
8. 外部字幕の重なりを ffmpeg(libass)で再現し、直した場面で名前に掛からないことを見た。
9. 音声認識: 誤り率 0.035(gen39b 0.038)。声の形は gen39b と同じ水準。
10. 確認用の束: クリップ 9 本を復号して誤り 0。確認ページの処理を簡易環境で動かした。`tests/test_review_pack.py` 9 件。
11. `build/gen34` - `gen39b` と元記事: sha1 一致、作業開始後の更新 0 件。
12. `.venv/Scripts/python.exe -m pytest` は、この記録を足したあとに通した(結果は `build/gen39c/eval/pytest_final.txt`)。
