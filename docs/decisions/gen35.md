## 判断

### 1. 先に「絵だけで何が分かればよいか」を決め、手段はそのあとで選んだ

人が挙げた 5 つと、記事の核心(ねじれる / ねじれない)を、**絵 1 枚ずつの合格条件** にしました。

| 絵だけで分かってほしいこと | そのために絵に要るもの |
| --- | --- |
| 左右の車輪がどこにあるか | 車輪が車輪に見えること(字を読まなくても) |
| 左右輪を何がつないでいるか | つなぐ部材が、全部の絵で同じ色であること |
| デフが車体側にあるとはどういうことか | **車体が描かれていること。**「一緒に上下する側」が囲まれていて、デフがその中か外かが見えること |
| ドライブシャフトがどこを通るか | デフから車輪まで、1 本の線として追えること |
| 教科書的な形とヴェゼルの形の、同じところと違うところ | 2 つが同じ向き・同じ描き方で並んでいること |
| ねじれる場合とねじれない場合の、左右輪の動きの違い | **片輪が持ち上がった状態** が描かれていて、反対側の車輪がどうなるかが見えること |

これを満たすには、形の違う部品・色の役目・傾いた車輪・破線の囲みが要ります。
**既存の 6 つの図解のどれを直しても届かない**(どれも、同じ形の箱に字を入れて並べる道具です)ので、
図解を増やす・直すのではなく、**絵を描いて画像として置く** ことにしました。
画像を置く書き方(`![](図.png)`)は前からあります。

### 2. 絵はスクリプトで描く。下地だけを道具に入れ、絵の中身は題材の側に置いた

gen34-2 は画像を「絵を外で手作りすることになり、今回だけの手作業」として退けていました。
**この理由は半分だけ正しい** と考えます。手で描いた画像を置けば、たしかに直すたびに描き直しです。
しかし「題材ごとに描く」こと自体は避けられません —— サスペンションの絵は、サスペンションの
話にしか使えません。**避けるべきなのは手作業であって、題材ごとの絵ではありませんでした。**

そこで 2 つに分けました。

* **どの題材でも同じになるところ** → `note2slides/sketch.py`(下地)。本文領域と同じ縦横比の画用紙、
  大きく描いて縮める、資料と同じ書体と色、ずらす・傾ける、引き出し線つきの名前。
* **題材ごとに違うところ** → シナリオの隣の `figures/draw.py`。何を、どの色で、どこに描くか。

下地に **機械の部品(タイヤ、バネ付きの車体など)を入れていません。** 入れると次の題材では
使われず、「今回のための機能」になります。`spring`(ジグザグ)と `hatch`(斜線)だけは、
題材を選ばない描き方なので入れています。

採らなかった案:

* **7 つ目の図解を作る**(部品の形を選べる配置図、など)。人が「特定の図解機能を追加することでは
  ない」と書いているとおりで、形の種類をいくら足しても、傾いた車輪やねじれた棒は書けません。
* **PowerPoint の図形として描く**(あとから人が動かせる)。座標で図形を置く書き方を
  シナリオに持ち込むことになり、シナリオが読めなくなります。絵を直したい人は `draw.py` を直せます。
* **外部の描画ライブラリ / 画像の生成。** Pillow(すでに依存に入っている)で届いたので足していません。
  生成画像は、記事が言っていない細部(部品の形、取り付け方)を勝手に描き込むので、
  今回の「断定していないことを描かない」と両立しません。
* **アニメーション。** 「動く前 → 動いたあと」は、破線(動く前の位置)と矢印で 1 枚に描けました。
  ねじれる / ねじれないの違いは **結果の形の違い** なので、静止画 2 枚を並べるほうが比べやすいと判断しました。

### 3. 見る向きを 2 つ使い、色の役目を全部の絵でそろえた

* **「デフが車体側にある」は、後ろから見た図でしか描けません。** 下から見た図では車体が
  画面の奥になり、デフが車体に付いているのか車軸に付いているのかが同じ絵になります。
* **「H の形」は、下から見た図でしか描けません。** 記事も下から見た形を書いています。

向きが 2 つあると混乱するので、**全部の絵の左上に「後ろから見た図」「下から見た図」と書きました。**
色は、青 = 左右輪をつなぐ部材、オレンジ = デフ、緑 = ドライブシャフト、斜線の灰色 = 車体で、
9 枚とも同じです。14 枚目(教科書的な形とヴェゼルの形)は、**共通の部品を同じ関数で描いています** ——
「同じところ」が、描いた側の都合ではなく本当に同じ絵になります。

### 4. 「ねじれる / ねじれない」は、絵にする必要があると判断した

人は「視覚的に理解できる必要があるかを再評価してください」と書いています。**必要です。**
gen34-2 は 28・29 枚目を「順に起きることなので `流れ` は合っている」として残しましたが、
この記事の結論は **「見た目が同じでも、ここがねじれるかどうかで動きが正反対になる」** です。
その「正反対」が画面の上で同じ形(3 つの箱と 2 本の矢印)をしていました。

描いたのは 4 枚です。

* **28 枚目**(一般的なトーションビーム)と **29 枚目**(古典的なド・ディオン)は、同じ構図です。
  同じ段差、同じ「片輪だけが持ち上がる」矢印。違うのは、つなぐ部材と反対側の車輪だけです。
* 「ねじれる」という言葉そのものが絵にならないと意味が無いので、**右上に小さな絵** を置きました
  (角棒の片方の端だけが回っている / 両方の端が同じ向きのまま)。最初は棒に斜めの縞を描いただけで、
  **ねじれではなく縞模様に見えました。** 次に斜めから見た角棒にしたら **くさびに見えました。**
  輪切りの線を足して、端から端へ向きが少しずつずれるのが見えるようにしています。
* **30 枚目** は、ヴェゼルの横ビームから二つの場合へ分かれる絵です。gen34-1 が「2 行の表で足りる」
  として見送った分岐図にあたります。表は読めますが、**28・29 枚目の絵と結び付きません。**
  同じ絵を小さく置くことで、「さっきの二つのどちらなのかが分からない」になります。
* **31 枚目** は、横ビームだけに色を残した絵です。

### 5. 記事が言っていないことを、どこまで描いたか

**絵は、言葉よりずっと多くを断定します。** 今回いちばん時間を使った判断です。

* **ヴェゼルの横ビームがねじれた絵は、描いていません。** 30 枚目の右の二つの絵は、
  「一般的なトーションビームの動き」「古典的なド・ディオンの動き」と **絵の中に** 書き、
  左下にも「ヴェゼルの動きを描いたものではありません」と書いています。
* **断りは、画面の文ではなく絵の中に入れました。** gen34-2 は画面の文で断っていましたが、
  絵だけが切り出されたとき(サムネイル、スクリーンショット)に付いていきません。
* **下から見た図に、上下の矢印を描くのをやめました。** 最初は 31 枚目の後輪の横に上下の矢印を
  描きましたが、下から見た図での画面の上下は **車の前後** です。矢印は「前後に動く」と読めます。
  その向きでは描けない動きなので、どの車輪の話かを囲みで指すだけにしました。
* **それでも、記事に無いものを置いています。** 一覧は成果物の README にあります
  (「絵にするときに、記事から足してしまったもの」)。いちばん重いのは **29 枚目の
  「反対側の車輪も一緒に傾く」** です。記事は「その影響は反対輪にも強く及びます」としか
  書いていません。「剛体の棒でつながっている」ことを絵にすると車輪は一緒に傾くので、そう描き、
  絵の中の言葉は記事に寄せて「一緒に動かされる」「強く及ぶ」にとどめ、「動きを大きく誇張した
  模式図」と断っています。**これが言い過ぎかどうかは、人に決めてもらう必要があります。**

### 6. 道具に警告や検査を足していない

「絵に断りが無い」「絵の文字が小さい」を機械で見る案は考えましたが、足していません。

README に「描くときに決めておくこと」として書く** ほうが正直だと判断しました。
