## 判断

### 1. 日本語も「機械が言い切れること」で絞り込む(`note2slides-reading`)

gen29 の線をそのまま日本語へ延ばしました。**正しい読みは決めない。読みが分かれることだけ
言う。**「方」を「ほう」と読むか「かた」と読むかは書いた人にしか決められませんが、
**「この語は 2 通りに読まれる」ことは原稿と関係なく言えます。**

だから **分かれる語だけを名指しし、どちらで読まれたかを添えます。** 効いたのは 2 つです。

* **occurrence ごとに見分ける。** 同じ「方」でも「進め方」はカタ、「古い方法」はホオで、
  どちらも正しい。まとめて 1 件にすると両方の音が現れ、**いつまでも「特定できません」**
  にしかなりません。読みごとに分けて初めて、確かめられる形になります。
* **含み合う候補は長いほうを採る。**「入って」の候補 ハイッテ / イッテ は、ハイッテ と
  読まれると **イッテ も必ず一致します。** ここを捨てないと、正しく読めている語が毎回
  挙がり、一覧そのものが読まれなくなります。

候補の仮名は表に書き写さず、**エンジンに聞いて** 作ります(gen29 が A-Z でやったのと同じ
理由。版が変われば仮名の書き方も変わる)。

**表に入れないものも決めました。**「何」「数」「間」「他」のように候補の仮名が短く
(ナン・スウ・マ・タ)、文中の別の語にもそのまま現れる表記です。見分けが付かないので、
挙げても毎回「特定できません」が並びます。**判定できないものを判定した風に出すと出力全体が
信用されなくなる**(gen29)——これは「出さない」側にも同じく効きます。

**合成前の警告には混ぜていません。** 読みが分かれること自体は間違いではないので、
`note2slides-audio` / `-video` の警告にすると毎回鳴って意味を失います。

### 2. 確認を、作ったあとから作る前へ移す(3 への答え)

人の 3 つ目の問いには、**手段ではなく手順で答えました。** このコマンドは前からありましたが、
README は「できたものを確かめる」道具として書いていました。**原稿を書いた側は、どちらの
つもりで書いたかを知っています。知っている側が直すほうが、あとから聞いて探すより確実です。**

今回それを自分で実行しました。**シナリオを書いた直後、音を 1 秒も作る前に** 掛けています。
出たのは 13 語で、目で追って 20 秒。そのうち **3 語が実際の誤読** でした
(値→ネ、通って→カヨッテ、通っている→カヨッテエル)。**人が gen29 で報告した 2 件と
同じもの** です。さらに、直したあとに残った「特定できません」の 1 行を追って
**「初めて聞く方に」→ ホオ** を見つけました。これは gen29 で人が見つけた
「見たい方は」→ ミタイホオワ と **同じ形の誤り** です。

**人が聞いて見つけたものが、作る前に出るようになりました。**

### 3. サムネイルを、収まったことを確かめてから出す

小さくしていき、**行数・幅・高さの 3 つで収まりを確かめてから返します。**
題は切り詰めません(書いていないものを出すことになる)。ただし、そこまで小さくなった題は
一覧では読めないので **警告で知らせます** ——「短い題を `--title` で指定してください」。

**崩さないことと、読めることを分けました。** 崩さないのは環境の責任、短い題を選ぶのは
書く人の判断です。人が PowerPoint へ逃げたのは、環境が **崩れたことを黙っていた** からで、
題が長かったからではありません。

### 4. 余った場所の渡し先を決める(5 への答え)

**文字の大きさは変えません。** 「書いたとおりの大きさで、どの道具で開いても同じに出る」は
gen28 が確立した前提なので、動かすのは置く場所だけにしました。

* 余りはまず図・図解へ。ただし **その中身が実際に使える分まで。** 横一列に並んだ流れは
  高さを渡しても大きくならず、渡しすぎると **図と次の中身のあいだが空くだけ** です
  (実測で、5 項目の横並びが使えるのは本文 5.05 inch のうち 0.71 inch)。
* それでも余ったら、**かたまりごと下げて縦中央へ。** 下に 1 行ぶんは残します
  (文章の高さは見積りなので、全部使うと実際が 1 行多いときに帯へ届く。gen28 の見え方)。

### 5. 見比べるための一覧を置いた(`--contact-sheet`)

gen29 の提案 3 が「3 回目に同じものを書いたら、そのとき置く」と書いていました。
**gen28 / gen29 / gen30 で 3 回目** なので置きました。**判定はしません** ——
何が正しい絵かを決められないのは gen28 / gen29 の結論のままで、今回も変わりません。
引き受けるのは **並べ方と番号** だけです。

実際、今回の欠陥は全部これで見つけました(場所の余り・表の潰れ・引用の 1 行化)。
1 枚ずつ開くと 44 回開くことになり、**そもそも見ないほうへ倒れます。**

### 採らなかった案

1. **正しい読みを環境に持たせる**(値→あたい を組み込む)。採りません。gen29 が
   `status`→ステータス で引いた線と同じで、**原稿に無いことを足す** ことになります。
   「値」は文脈によっては「ね」が正しい語です。
2. **読み方辞書をシナリオの front matter に書けるようにする。** 見送り(下記)。
3. **文章も場所が余ったら大きくする。** 採りません。画面ごとに文字の大きさが変わると、
   動画では画面が変わるたびに字の大きさが動きます。gen28 の前提とも衝突します。
4. **図解の種類に「対比」を足す**(人間側 / AI側 を左右に並べる)。見送り(下記)。
