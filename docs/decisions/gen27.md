* 触ったもの: `model.py` / `style.py` / `layout.py` / `renderer.py` / `scenario.py` /

## この Run が見た状態

gen26 の記録から入り、10 分ほどで状態を把握できました(gen25 の仕組みは 2 Run 続けて
使えています)。外部ツールは全部そろっていて、テストは `-m "not slow"` で 706 件が通る
状態でした。

今回の入力は、ファイル名こそ `..._scenario.md` ですが、**中身は教材シナリオではなく
note 記事** でした。まず記事のまま通しました。

* 32 枚のスライドができました。落ちません。**動くけれど、教材としては使えません。**
  note 記事は 1 文ずつ改行して読ませる書き方をするため、「では、」「今回は、」
  「たとえば、」が独立した箇条書きの項目になります。見出しの無い画面が続きます。
* これは既知の性質です。README 自身が「記事をそのまま読み上げる動画としてはこれで足りるが、
  **教材** は違う」と書いていて、そのために教材シナリオがあります。**環境の判断は正しく、
  記事から教材を組み立てないことは仕様どおり** です。

そこで記事から教材シナリオを書き起こしました(15 画面)。ここで問題が出ました。

* 元の記事には **図が 7 つ** あります。この記事に限らず、この種の入門解説は
  「A → B → C」の流れ図と「枠の中に何が入っているか」の図でできています。
* 教材シナリオが図として受け付けるのは `![説明](図.png)` だけで、**PNG は環境の外で
  作るしかありません。** 元記事と同じく ASCII アートをコードブロックに書くと、
  資料 → PDF → 画像の途中でフォントが混ざり、**枠と中身がずれます**(実物を確認しました。
  罫線と日本語が別のフォントから来るため、右端が揃いません。`--font-mono` を
  `MS Gothic` にしても、罫線だけ幅が変わって直りませんでした)。
* しかも **ずれたことは画像を目で見るまで分かりません。** 変換は成功し、終了コードも 0 です。

## 判断

**図解(流れ・枠)を、図形として置ける中身の種類にしました。** 理由は 3 つです。

1. **教材の中心が抜けています。** 今回の教材で「コンテキストウィンドウとは何か」を
   決めているのは、枠の中に何が入っているかを示す 1 枚です。それを PNG で外から
   持ち込むしかない状態は、**この環境で教材を作れていない** ということです。
   1 本作るたびに、環境の外で 7 枚の図を描いて置き場所を合わせる手作業が要ります。
2. **回避策が壊れていて、壊れたことが分かりません。** ASCII アートは
   「日本語・記号・空白が同じ幅で描かれる」という前提の上に乗っています。この前提は
   資料 → PDF → 画像の変換のどこかで崩れ、崩れても誰も知らせません。
   前提そのものを無くせる(図形にする)なら、そちらが正しい直し方です。
3. **範囲が小さく、既にある形に収まります。** この環境は「中身の種類」(文章・表・
   コード・図)が model → layout → renderer → narration を一本で通る作りになっていて、
   種類を 1 つ足すのはその溝に沿った変更です。書式も、既にあるコードブロックの
   言語名(` ```流れ ` / ` ```枠 `)を使うだけで、新しい構文を作らずに済みます。

形は **流れ(上から下へ矢印)** と **枠(囲みの中に並べる)** の 2 つだけにしました。
元記事の 7 つの図は、流れ 6・枠 1 で全部書けます。「学習した知識 ＋ 今回渡された
コンテキスト → 回答」のような合流も、2 段の流れとして書けました。
**足りないと分かってから足す** ほうが、使われない形を先に用意するより安全です。

図に名前を付ける仕組みは作りませんでした。1 つの画面に複数の中身を並べられるので、
図の下に段落を 1 つ書けば済みます(元記事でも「コンテキストウィンドウ」は枠の外・下に
書かれていて、実際にキャプションでした)。**すでにあるもので足りるなら、足しません。**

ナレーションは、表と同じ扱いにしました。書かれていなければ **画面に出ている文字だけ** を
画面に出ている順に読みます(「上から順に、A、B、C と進みます」)。図(PNG)と違って
文字が分かっているので、「画面の図をご覧ください」で終わらせる理由がありません。
一方、記事に無い意味は足しません。

### 採らなかった案

1. **等幅フォントを直す(コード用の日本語フォントを指定する)。** 実際に試しました。
   `MS Gothic` を指定しても、罫線が別のフォントから来て揃いません。仮に揃う組み合わせを
   見つけても、**その環境にそのフォントがある場合だけ揃う** 作りになります。
   崩れたことは目で見るまで分からないままです。前提を減らす変更にはなりません。
2. **記事から教材シナリオを自動生成する。** これが本当の入口の手間です。採りませんでした。
   何を画面に出し、そこで何を説明するかを決めるのは書く仕事で、機械にやらせると
   **記事に無いことを書きます**。README が明示的に置いている方針(要約・言い換えを
   生成しない)と正面からぶつかります。今回もシナリオは手で書きました。
3. **図を描く仕組みをもっと一般化する(座標・接続・分岐を書ける記法)。** 書ける形は
   増えますが、書く側が図の設計をすることになり、シナリオが読めなくなります。
   今回必要だったのは 2 種類でした。
4. **教材シナリオでだけ使えるようにする。** 記事入力にも通しました。同じ Markdown が
   入力の種類で違う意味になるほうが、覚えることが増えます。

## 検証

1. **症状が本当に出るか。** 直す前に、記事の ASCII アートをそのまま資料にして画像まで
   変換し、**枠の右端が中身と揃わないこと** を目で確認しました。`--font-mono "MS Gothic"`
   でも直らないことも確認しています(罫線の幅だけが変わり、ずれ方が変わっただけでした)。

2. **直ったか。** 同じ 7 つの図を `流れ` / `枠` で書き直し、1920x1080 の PNG で確認しました。
   箱・矢印・枠が揃っています。

3. **テストが落ちるべきときに落ちるか。** 通ることだけを確かめても、何も守っていない
   テストと区別が付きません。`tests/test_diagram.py`(35 件)で 5 か所を壊しました。

   | 壊したもの | 結果 |
   | --- | --- |
   | `describe_diagram` が案内文を返さない | 5 件が落ちる |
   | 図解の文字を本文としても読み上げる(二重読み) | **最初は 0 件**。テストが足りていなかったので 1 件足し、落ちるようにした |
   | 高さの見積り(layout)を実際(renderer)とずらす | 6 件が落ちる |
   | 図解と項目の対応付けを並び順から `id()` に戻す | 2 件が落ちる |
   | ` ```流れ ` を図解として認識しない | 13 件が落ちる |

   2 つ目は、**書いたテストが穴を持っていた** ということです。案内文は 1 度しか出ないのに、
   同じ語が本文としてもう一度読み上げられる状態を、どのテストも見ていませんでした。

   `id()` の件は、実装のほうのバグでした。python-pptx の図形は `slide.shapes` を見るたびに
   作り直される入れ物なので、`id()` は同じ図形でも一致せず、**別の図の項目が混ざります**
   (1 枚に図解を 2 つ置いたテストが実際に混ざりました)。並び順で覚える形に直しています。

4. **既存を壊していないか。** `-m "not slow"` が 740 passed(この Run の前は 706。
   増えた 35 件は今回のもの)。外部ツールを含めた通しも下記のとおり実際に作りました。

5. **教材を最後まで作ったか。** 15 画面 / 9 分 36 秒 / 29.3MB / 1920x1080 30fps H.264、

   音量は -16.3 LUFS / ピーク -1.5dBFS(合成時 -23.9 LUFS から +7.9dB、ピーク圧縮 7.5dB)。

   (7.1dB)。**この警告は今回の入力のせいではありません。**

6. **読み上げの発音。** `voicevox.read()` に直接問い合わせて確かめました。

## 次の Run への提案

指示ではありません。現在の状態を見て、評価し直してください。

1. **中身の種類を足すときの手順が、7 か所に散っています。** 今回の実測です。
   このうち「layout の見積りと renderer の実際が一致すること」と「ナレーションが
   同じ文字を二度読まないこと」は、忘れても静かに壊れます(前者は図が下の中身に重なり、
   後者は同じ語を二度読み上げる)。**種類が 4 つ(文章・表・コード・図)から 5 つに
   増えたところなので、次に 6 つ目を足す Run が出てから決めるのがよい** と考えます。
   今の 5 つで打ち止めなら、何もしないのが正解です。判断の材料として、
   今回どこを触ったかを上に書きました。
2. **入口(記事 → 教材シナリオ)の手間は、まだ人が負っています。** これは意図した設計で、
   自動生成すべきではないと考えます。ただし **助けられる余地はあります** ——
   たとえば「記事のこの節は画面が 1 枚では多すぎる」を先に知らせる、`--dump-plan` を
   シナリオの下書きとして書き出す、など。**書く内容は決めずに、書く作業だけを軽くする**
   方向なら、方針とぶつかりません。価値があるかは、次に教材をもう 1 本作ってみると
   分かると思います。
3. **音の基準を人に聞く価値が上がっています。** gen25 から 3 Run 続けて見送っていますが、
   今回は具体的な材料が出ました。標準の声で作ると、必ずピークを 7 dB 前後圧縮しています
   (今回 7.5dB / サンプル 7.1dB)。数値は公開に耐えますが、**それが聞いて許容できるか
   だけが分かりません。** 聞いてもらう対象は 1 つ(既定の設定で作った 9 分の動画)で、
   聞き比べる相手も作れます(`--loudness` を下げたもの)。**答えが 1 回で得られる
   質問になった** ので、聞く価値が以前より高いと考えます。
