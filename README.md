# Agentic Development Evolution Experiment

最小限のAI開発環境から実際のソフトウェア開発を始めたとき、開発環境そのものがどのように変化していくかを観察する実験です。

## 開発対象

note記事を入力として、eラーニング形式のYouTube通常動画を生成するシステムを開発します。

想定する最終成果物は、記事からプレゼンテーション資料、スライド画像、ナレーション音声を生成し、それらを組み合わせた動画です。

## 実験方針

完成した開発環境を最初から設計しません。

実際の開発を進める中で、現在の開発環境に不足や問題があるとAIが判断した場合は、開発環境そのものも改善対象とします。

改善の方法や構造はあらかじめ決めません。

特定の手法や構造の導入を前提とせず、実際の開発で必要と判断された改善を行います。

必要な仕組みが生まれなかった場合も実験結果として扱います。

開発は Run(AI の 1 セッション)ごとに進みます。「今どうなっているか」はコードと README と
Git 履歴に残りますが、「なぜそう決めたか」「何を見送ったか」は残らないため、Run ごとの判断は
[`docs/decisions/`](docs/decisions/README.md) に記録しています。過去の判断は指示ではなく、
次の Run が評価し直すための材料として置いてあります。

---

## note2slides

記事や **教材シナリオ** から、16:9 のプレゼンテーション資料(.pptx)と、ナレーション付きの動画(.mp4)を生成します。
入力は、手元の Markdown ファイルでも、**公開されている note 記事の URL** でも構いません。

```
記事(.md) / 公開 note 記事の URL / 教材シナリオ(.md)
    --[note2slides]--> 資料(.pptx) --[note2slides-video]--> 動画(.mp4)
    |                                   |
    |                                   +--[note2slides-images]--> slide_001.png ...
    |                                   +--[note2slides-audio]---> narration_001.wav ...
    |                                   +--> sample.srt(字幕)
    |                                   +--> sample_chapters.txt(概要欄の章立て)
    |
    +--[note2slides-thumb]--> thumbnail.png(投稿に使う 1 枚絵)

note2slides-reading  資料(.pptx) -> 何と読まれるか(仮名)。音を作らずに読み違いを見つける
```

入力は 2 通りあります。**記事** を渡すと、記事の文章構造から動画の構成を組み立てます
(記事をそのまま読み上げる動画になります)。**教材シナリオ** は、「この画面にこれを出し、
ここでこう説明する」を先に決めて書いたもので、書いたとおりの画面とナレーションになります
(→ [教材シナリオから動画を作る](#教材シナリオから動画を作る))。
資料になったあとの処理は同じで、画像・音声・動画のコマンドはどちらでもそのまま使えます。

画像と音声は同じ番号(スライド番号)で対応します。`slide_001.png` に対応する音声が `narration_001.wav` です。
動画生成はこの 2 つを呼び出すので、資料から動画までは 1 コマンドで作れます。

資料は Office Open XML なので、PowerPoint でも LibreOffice Impress でも開いて編集できます。

### セットアップ

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -e ".[dev]"   # Windows
# .venv/bin/python -m pip install -e ".[dev]"         # macOS / Linux
```

外部ツールは、使う機能に応じて必要になります。どれも無くても資料(.pptx)は生成できます。
PowerPoint は不要です。

| ツール | 必要な機能 | 無い場合 |
| --- | --- | --- |
| [LibreOffice](https://ja.libreoffice.org/) | スライド画像 / 動画 | PDF を直接入力すれば不要 |
| [VOICEVOX](https://voicevox.hiroshiba.jp/) | ナレーション音声 / 動画 | Windows 標準の音声合成に切り替わる(声の質は落ちます) |
| [VOICEVOX Nemo](https://voicevox.hiroshiba.jp/nemo/) | **標準のナレーション音声** | VOICEVOX の声(No.7 / アナウンス)に切り替わります |
| ffmpeg | 動画 | 上の `pip install` で同梱のものが入るため、別途の導入は不要 |

VOICEVOX Nemo は VOICEVOX の「設定 > エンジン」から追加します(追加すると
`--engine voicevox-nemo` で使えます)。声は「女声1〜6 / 男声1〜3」で、
キャラクターとしての人格を持ちません。
標準のナレーションはこの中の **「男声3 / ノーマル」** です
(→ [標準のナレーション音声](#標準のナレーション音声))。

### 使い方

```bash
# 記事 -> 資料
.venv/Scripts/python.exe -m note2slides.cli samples/sample_article.md -o build/sample.pptx

# 教材シナリオ -> 資料(画面とナレーションを書いたとおりに作ります)
.venv/Scripts/python.exe -m note2slides.cli samples/lesson_scenario.md -o build/lesson/lesson.pptx

# 公開 note 記事の URL -> 資料(記事中の画像も取り込みます)
.venv/Scripts/python.exe -m note2slides.cli https://note.com/sane_mink364/n/na01bf3bed64d \
    -o build/token/token.pptx

# 資料 -> ナレーション付き動画(スライド画像と音声も同時に作ります)
.venv/Scripts/python.exe -m note2slides.video_cli build/sample.pptx -o build/sample.mp4

# 資料 -> スライド画像
.venv/Scripts/python.exe -m note2slides.images_cli build/sample.pptx -o build/slides

# 資料 -> ナレーション音声
.venv/Scripts/python.exe -m note2slides.audio_cli build/sample.pptx -o build/audio

# 記事 / 教材シナリオ -> 投稿用のサムネイル画像
.venv/Scripts/python.exe -m note2slides.thumbnail_cli samples/lesson_scenario.md \
    -o build/lesson/thumbnail.png --label "第1回"

# 記事 -> ナレーション音声の候補(聴き比べて標準の声を決めるため)
.venv/Scripts/python.exe -m note2slides.voice_compare_cli samples/narration_sample.md -o build/voice_compare
```

資料生成(note2slides)の主なオプション:

| オプション | 説明 |
| --- | --- |
| `-o, --output` | 出力先(既定は入力と同じ場所・同じ名前の .pptx) |
| `-f, --force` | 出力先が既にある場合に上書きする |
| `--title` | 表紙のタイトルを指定する |
| `--theme` | スライドの見た目(`light` / `plain`。既定は `light`) |
| `--no-split-sentences` | 段落を文単位に分けず、1 段落を 1 項目にする |
| `--no-notes` | 発表者ノートに元の本文を入れない |
| `--font-latin` / `--font-ea` / `--font-mono` | 欧文 / 日本語 / 等幅フォント |
| `--dump-plan PATH` | スライド構成を JSON で書き出す(確認・差分比較用) |
| `--scenario` | 入力を教材シナリオとして読む(シナリオでない場合はエラーにする) |

`--title` 以外の構成に関わる指定(`--no-split-sentences` / `--no-notes` / `--no-title-slide`)は、
記事から構成を組み立てるときのものです。教材シナリオには構成が書かれているため、
指定された場合は黙って無視せずエラーにします。

URL を入力にする場合のオプション:

| オプション | 説明 |
| --- | --- |
| `--image-dir DIR` | 取り込んだ画像の置き場所(既定は出力と同じ場所の `<名前>_images`) |
| `--dump-article PATH` | 取り込んだ記事を JSON で書き出す(本文の欠落・混入の確認用) |
| `--fetch-timeout` / `--user-agent` | 取得の待ち時間(秒、既定 30)と User-Agent |

### スライドの見た目

見た目は `--theme` で選びます。既定は `light` です。

| テーマ | 見た目 |
| --- | --- |
| `light` | 表紙は濃い地に白い文字、章扉はうすい地、本文は白地。本文には資料名とページ番号が入ります |
| `plain` | 白地のみ・装飾なし(以前の見た目) |

画面の役割ごとに地の色を変えているのは、動画にしたときに「表紙 → 章 → 本文」の
切り替わりが分かるようにするためです。色や位置は `style.py` の `Theme` にまとまっています。

**タイトルの改行** は、幅に入るところで機械的に切るのではなく、文節の切れ目を探して
決めます(`text_wrap.py`)。「開発環境をゼロか / ら作り直す」のように語の途中で
切れることを避け、行の長さもなるべくそろえます。行頭に `、` や `」` が来ないなどの
禁則も見ます。

```
生成AIを前提とした開発環境を        <- 表紙(40pt)は 2 行に
ゼロから作り直すための実践ガイド
```

### 記事の書き方とスライドの対応

記事を入力にした場合の対応です(教材シナリオは
[教材シナリオから動画を作る](#教材シナリオから動画を作る) を参照してください)。

| Markdown | スライド上の扱い |
| --- | --- |
| front matter の `title` / `subtitle` | 表紙 |
| `#` 見出し | 表紙と同じ内容なら表紙に統合、異なる場合は章扉 |
| `##` 以下の見出し | スライドの区切りとタイトル |
| 段落 | 文ごとの箇条書き(発表者ノートには段落のまま残す) |
| 箇条書き / 番号付きリスト | 箇条書き(入れ子は字下げ、番号は元の数字を維持) |
| 引用 | 縦線付きの項目 |
| コードブロック | コード用スライド |
| 表 | 表スライド |
| ローカル画像 | 画像スライド(参照先が無い場合は警告を出し、本文に `[画像] 代替テキスト` として残す) |
| `---` | 明示的なスライド区切り |

1 枚に収まらない場合は自動で次のスライドへ送り、タイトルに「（続き）」を付けます。
発表者ノート(ナレーションの読み上げ元)には、**そのスライドに出ている分だけ** を入れます。
まとめて 1 枚目に入れると、まだ画面に出ていない文を読み上げてしまうためです。

### 本文の扱いについて

スライドに載る文章は、記事の本文をそのまま並べ替えたものです。
要約・言い換え・補足の生成は行いません(記号の除去と、文単位への分割のみ行います)。
言い回しを変えたい場合は、生成後のファイルを直接編集するか、元の記事を修正してください。

文単位に分けるとき、**括弧の中の句点・疑問符では切りません**。

```
今回は「そもそもAIは文章をどう扱っているのか？」というところから、順番に整理してみます。
```

「？」で切ると、1 つの文が 2 行に割れて画面に出るうえ、読み上げでも
「〜のか？」で言い切ってから「というところから〜」を読み直したように聞こえます。
括弧の閉じ忘れがある場合は切らない側に倒れます(切り所を間違えるより、行が長くなる
ほうが害が小さく、長い行は読み上げ側が読点で区切ります)。

ナレーションも同じ方針です。表・コードのように文字として読み上げられないものだけ、
画面に出ている文字を使って「どこを見ればよいか」を案内します
(→ [画面に出ているものの案内](#画面に出ているものの案内表コード図))。

## 教材シナリオから動画を作る

記事を入力にすると、記事の文章構造から動画の構成を組み立てます。記事をそのまま読み上げる
動画としてはこれで足りますが、**教材** は違います。何を画面に出し、どの図を見せ、そこで何を
説明するかは、記事の書き方とは別に決めるものだからです。

教材シナリオは、それを先に決めて書く入力です。**画面に出すもの**と**読み上げる文章**を別々に
書き、書いたとおりの枚数・順番で動画になります。構成を組み立て直すことはしません。

```bash
.venv/Scripts/python.exe -m note2slides.cli samples/lesson_scenario.md -o build/lesson/lesson.pptx
.venv/Scripts/python.exe -m note2slides.video_cli build/lesson/lesson.pptx -o build/lesson/lesson.mp4
```

資料になったあとは記事から作った場合とまったく同じで、スライド画像・ナレーション音声・動画の
コマンドも、声・間・音量の指定もそのまま使えます。

### 書き方

`samples/lesson_scenario.md` が動く例です。先頭の front matter に `type: scenario` と書いた
Markdown が教材シナリオになります(この宣言だけで見分けるので、記事の扱いは変わりません)。

```markdown
---
type: scenario
title: 教材シナリオから動画を作る
---

## この教材で学ぶこと

### 画面

- 画面に出す文字はここに書く
- 箇条書きも図も表もここに書く

### ナレーション

この画面では、学ぶことを三つ挙げています。

段落を空けると、そこが読み上げの区切りになります。
```

`##` が 1 枚の画面です。見出しがそのままスライドのタイトルになります。

| 書くところ | 内容 |
| --- | --- |
| `## 見出し` | 1 枚の画面。見出しがスライドのタイトルになる |
| `### 画面` | 画面に出すもの(文章・箇条書き・図・表・コード) |
| `### ナレーション` | その画面で読み上げる文章 |
| `### 設定` | レイアウトと見る時間(省略できる) |

見出しは英語(`screen` / `narration` / `settings`)でも書けます。
`### 画面` と `### ナレーション` はどちらも省略できます(画面だけ・音声だけの画面も作れます)。

### 画面に書けるもの

`### 画面` の中は Markdown です。次のものを書けます。

| 書き方 | 画面 |
| --- | --- |
| 段落 | 記号を付けずに、そのまま 1 行として出す(説明の文) |
| `-` / `1.` の箇条書き | 箇条書き(入れ子は字下げ、番号は元の数字を維持) |
| `> ` の引用 | 縦線付きの行 |
| `![説明](図.png)` | 図(説明は図の下にキャプションとして出る) |
| 表 | 表 |
| ` ```流れ ` のブロック | 図解: 上から下へ、矢印でつなぐ(→ [図解を書く](#図解を書く流れ枠)) |
| ` ```枠 ` のブロック | 図解: 枠の中に並べる(→ [図解を書く](#図解を書く流れ枠)) |
| ` ``` ` のコードブロック | コード(枠の中に等幅で出る) |

**1 つの画面に、複数の中身を並べられます。** 文章と図、表と補足の文、コードとその説明を
1 枚に置けます。並ぶ順は **シナリオに書いた順** で、上から下へ縦に並びます。

```markdown
## 教材シナリオから動画ができるまで

### 画面

工程は三つあります。シナリオを書き、資料を作り、動画にします。

![シナリオ、資料、動画の三つの工程](figure.png)

### ナレーション

画面の図をご覧ください。左から順に、教材シナリオ、資料、動画と並んでいます。
```

ナレーションは **画面ごとに 1 つ** のままです。中身の 1 つずつに対応させる必要はなく、
その画面全体について説明する文章を書きます(画面とナレーションの対応は 1 画面 = 1 本の
まま変わりません)。

図のパスは **シナリオファイルからの相対パス** です。指定した図が見つからない場合は、探した
場所を示して中断します(教材では、figure が抜けたまま動画にしても直しようがないためです)。

1 枚に収まらない量を書いた場合も、勝手に次の画面へ送りません。小さく表示して収めたうえで
警告を出すので、画面を分けるかどうかはシナリオ側で決めてください。図(`![](図.png)`)と
図解(流れ・枠)は縮めても読めるので、場所が足りないときは **まず図が譲ります**
(文章・表・コードが入りきらない場合だけ警告します)。

逆に、**場所が余った場合** はこう決まります。

* 余りはまず、**大きく描ける中身**(図・図解)に渡します。ただし渡すのは
  **その中身が実際に使える分まで** です。横一列に並んだ流れは高さを渡しても
  大きくならないので、渡しすぎると図と次の中身のあいだが空くだけになります。
* それでも余る場合は、**中身のかたまりごと下げて縦中央に置きます。** 文章・表・コードは
  広い箱をもらっても大きくならないため、上に貼り付いたままだと画面の下半分が丸ごと空きます。
  2 行しか書いていない画面が、見ている側には作りかけに見えます(動画では 20 秒それを見ます)。
* **文字の大きさは変えません。** 書いたとおりの大きさで出すのが前提なので、動かすのは
  置く場所だけです。

小さくするときは、**文字の大きさそのものを書き換えます**。「この枠は何割で表示する」という
指示(`normAutofit` の `fontScale`)は PowerPoint しか見ないため、それを使うと資料では
収まっているのにスライド画像と動画でははみ出す、という食い違いが起きます。
同じ理由で、ひな型のレイアウトが持っている文字の変換(章扉の「すべて大文字」など)も
打ち消します。**書いたとおりの文字が、どの道具で開いても同じ大きさで出ます。**

### 図解を書く(流れ・枠)

工程や関係を示す図は、` ```流れ ` と ` ```枠 ` で書きます。**1 行が 1 つの項目** で、
書いた順に上から並びます。箱と矢印は図形として置かれるので、拡大しても縮小しても崩れません。

````markdown
### 画面

```流れ
これまでの会話
今回の質問
モデルへ入力
回答を生成
```
````

| ブロック | 図 |
| --- | --- |
| ` ```流れ ` (`flow`) | 項目を矢印でつなぐ(工程・順番) |
| ` ```枠 ` (`frame`) | 項目を 1 つの枠の中に並べる(何が含まれているか) |

**並べ方と大きさは、書かなくても決まります。**

* **流れは、横に並べて収まるならそのまま横に並びます**(`AI → MCP → AWS`)。「A から B へ」は
  左から右へ読むほうが自然で、縦に積むと画面の左右が大きく空きます。項目が長くて 1 行に
  収まらない場合だけ、縦に積みます(文字を折り返してまで横には並べません)。
  向きは案内文にも合わせます(「左から順に」/「上から順に」)。
* **渡された場所に合わせて大きさが決まります。** 図解は絵なので、場所が余っていれば
  そのぶん大きく描きます(小さく描いても伝わる内容は増えません)。ただし
  **文字はスライドの見出しより大きくしません**(図の中の語が、その画面の題より
  目立つことにならないように)。
* 図解と文章が並ぶ画面では、**余った場所は図解に渡します**。文章は広い箱をもらっても
  大きくならないためです。ただし全部は渡さず、文章の折り返しが 1 行増えても収まる分は
  残します。

図に名前を付けたい場合は、図解の下に段落を 1 つ書いてください
(1 つの画面に複数の中身を並べられます)。

````markdown
### 画面

```枠
これまでの会話
渡された資料
今回の質問
```

この枠がコンテキストウィンドウです。
````

**なぜコードブロックの ASCII アートではないのか。** 罫線や矢印を文字で並べる書き方は、
「日本語・記号・空白が同じ幅で描かれる」ことを前提にしています。資料 → PDF → 画像と
変換する途中で 1 つでも別のフォントが使われると、枠と中身がずれます。しかも、ずれたことは
**画像を目で見るまで分かりません**。図形として置けば、この前提そのものが要らなくなります。

項目が 6 個を超えると、1 つ 1 つが小さくなるため警告を出します(画面を分けるかどうかは
シナリオ側で決めてください)。図解は記事入力でも同じ書き方で使えます。

ナレーションを書かなかった場合は、**画面に出ている文字だけ** を使って案内文を作ります
(表と同じ考え方です。並べ替えたり、そこから言えることを足したりはしません)。

```
画面の図をご覧ください。上から順に、これまでの会話、今回の質問、モデルへ入力、回答を生成と進みます。
画面の図をご覧ください。枠の中には、これまでの会話、渡された資料、今回の質問が入っています。
```

### ナレーションの書き方

`### ナレーション` に書いた文章が、その画面が映っている間の音声になります。
**空行で分けた段落が、読み上げの区切り**(行)になります。段落の中の改行はつながって
1 行になるので、書きやすい幅で折り返して構いません。

```markdown
### ナレーション

画面の図をご覧ください。

左から順に、教材シナリオ、資料、動画と並んでいます。
```

読み上げの間・速さ・声は記事入力と同じです(→ [聞きやすさのために行っていること](#聞きやすさのために行っていること))。
文と文の間は 0.35 秒、行の間は 0.6 秒で、1 枚分はひと続きに読み上げます。

表・コード・図の画面でも、**ナレーションに書いた文章がそのまま読み上げられます**。
画面の案内文(「画面の表をご覧ください」など)を組み立てるのは、ナレーションを書かなかった
場合の記事入力だけです。図の内容を説明できるのは書いた人だけなので、ここは推測しません。

### 設定(レイアウトと見る時間)

```markdown
## 教材シナリオから動画ができるまで

### 設定

- レイアウト: 表紙
- 見る時間: 2
```

| 設定 | 値 | 意味 |
| --- | --- | --- |
| `レイアウト` | `本文`(既定) | タイトルと内容の画面 |
| | `表紙` | 大きなタイトル。`### 画面` に書いた文章が副題になる |
| | `章扉` | 見出しだけを大きく映す |
| `見る時間` | 秒数 | 読み終わったあとに画面を見せる時間 |

`見る時間` は、図や表を読む時間を作るためのものです。ナレーションを書かなかった画面では、
**その秒数だけ映して次へ進みます**(書かなかった場合は `--silence` の既定 2 秒)。
英語(`layout` / `hold`、`body` / `cover` / `section`)でも書けます。

### シナリオが正本であること

シナリオに書いた画面とナレーションは、動画になるまで変わりません。

* `### 画面` に書いたものだけがスライドになります。ナレーションは画面に出ません。
* `### ナレーション` に書いた文章だけを読み上げます。画面の文字を代わりに読むことはしません。
* ナレーションを書かなかった画面は**無音**です。画面の文字を読み上げて埋めることはしません。

ナレーションは資料の**発表者ノート**に入ります。文章では表せない指定(読み上げないこと・
見る時間)だけは、ノートに指示行として残ります。資料を PowerPoint で開いて直接直すこともできます。

```
[note2slides] hold=2
[note2slides] narration=none hold=4
```

### 直したいとき

シナリオを直して、もう一度資料と動画を作り直すのがいちばん簡単です。読み方だけを直す場合は、
記事入力と同じく読み方辞書や原稿(`script.json`)でも直せます
(→ [読み方を直したいとき](#読み方を直したいとき))。

### 書き間違えたとき

シナリオは動画構成の正本なので、書き間違いを別の構成に倒さず、場所を示して中断します。

```
lesson.md の 5 行目（1 枚目「作る流れ」）: 画面に指定した図が見つかりません: pipeline.png
  探した場所: D:\work\lesson\pipeline.png
  シナリオのある場所からの相対パスで書いてください(教材シナリオでは、指定した図が無いまま動画にはしません)。
```

| 症状 | 確認すること |
| --- | --- |
| 教材シナリオとして読まれない | front matter の `type: scenario`。`--scenario` を付けると、無い場合にエラーになります |
| 「どの画面のものか分からない文章があります」 | 文章が `### 画面` か `### ナレーション` の下にあるか |
| 「知らない見出しです」 | `###` の名前。書けるのは 画面 / ナレーション / 設定 です |
| 「1 枚に収まらない可能性があります」 | 1 画面の中身の量。減らすか、`##` を足して画面を分ける |
| 「図の中身が空です」 | ` ```流れ ` / ` ```枠 ` のブロックの中。1 行に 1 つずつ項目を書く |
| 図にしたいものがコードとして出る | ブロックの名前。図解になるのは `流れ` / `枠`(`flow` / `frame`)だけ |
| 画面に出したい文字が読み上げられている | `### 画面` ではなく `### ナレーション` に書いていないか |
| 思ったより画面が多い / 少ない | `##` の数。`--dump-plan` で構成を書き出して確認できます |

## 公開 note 記事の URL を入力にする

記事を手元のファイルへ写さずに、公開されている note 記事の URL をそのまま渡せます。

```bash
.venv/Scripts/python.exe -m note2slides.cli https://note.com/sane_mink364/n/na01bf3bed64d \
    -o build/token/token.pptx --dump-article build/token/article.json

.venv/Scripts/python.exe -m note2slides.video_cli build/token/token.pptx -o build/token/token.mp4
```

```
build/token/
  token.pptx          資料
  token_images/       記事から取り込んだ画像(image_001.png ... 掲載順の連番)
  article.json        取り込んだ記事の内容(--dump-article)
```

出力先を指定しない場合は、記事キー(`na01bf3bed64d.pptx`)が名前になります。
資料になったあとは、ファイルから作った場合とまったく同じで、画像・音声・動画の
コマンドもそのまま使えます。

### ページ HTML ではなく、記事本文だけを取る

取得先は note が公開している **記事 API**(`https://note.com/api/v3/notes/<記事キー>`)です。

```
https://note.com/<ユーザー>/n/<記事キー>
    -> https://note.com/api/v3/notes/<記事キー>  ->  data.body(記事本文の HTML)
```

ページの HTML を読むと、ナビゲーション・関連記事・広告・プロフィール・コメント欄も
一緒に入ってくるので、あとから「どれが本文か」を判断することになります。API の `body` は
**記事本文だけ** なので、本文でないものが混ざる余地がそもそもありません。
記事本文の文字は 1 文字も足さず、削らずに取り込みます
(`tests/test_note_source.py` と `tests/test_note_source_live.py` で、本文 HTML の可視文字と
取り込んだ文字が一致することを確認しています)。

### note の記事とスライドの対応

| note の本文 | スライド上の扱い |
| --- | --- |
| 記事タイトル | 表紙(著者名と公開日を副題に入れます) |
| 見出し(大 / 小) | スライドの区切りとタイトル |
| 段落 | 文ごとの箇条書き(発表者ノートには段落のまま残す) |
| 段落の中の改行 | 行だけを変える(段落は分けない) |
| 箇条書き / 番号付きリスト | 箇条書き(入れ子は字下げ、番号は元の数字を維持) |
| 引用 | 縦線付きの項目 |
| コード | コード用スライド |
| 表 | 表スライド |
| 画像(キャプション付きを含む) | 画像スライド(**本文の中の位置と掲載順のまま**) |
| 区切り線 | スライドの区切り |
| 太字 / 斜体 / リンク / ふりがな | そのままの書式(ふりがなは本文の側を使う) |

画像は表示用に縮小されたものではなく **原寸** を取り込みます(スライドは 1920 幅で
描画するため、表示用の大きさだと粗く見えます)。取り込んだ画像は掲載順の連番で
`--image-dir` に残るので、記事のどこにあった画像かを後から確認できます。

見出し画像(サムネイル)は記事本文ではないため取り込みません。

対応付けを持たない要素に出会った場合は、**中の文章は捨てずに** 取り込み、
どの要素だったかを警告に出します(本文が黙って消えるより、知らない装飾が
残るほうが確認しやすいためです)。

### 扱わない記事

| 記事 | 動き |
| --- | --- |
| ログインが必要な記事 | 取得の時点で理由を示して中断します |
| 有料部分のある記事 | 同上(無料で読める範囲だけを取り込むと本文が欠けるため) |
| 下書き・非公開の記事 | 同上 |
| note 以外のサイト | URL を見た時点で断ります(通信しません) |

### 取り込みに失敗したとき

失敗したときのメッセージには、記事の URL・実際に叩いた API・HTTP の応答が載ります。

```
記事を取得できませんでした: https://note.com/xxx/n/nzzzz
  取得先: https://note.com/api/v3/notes/nzzzz
  HTTP 404 Not Found
  記事キーが違うか、記事が削除・非公開になっている可能性があります。
  応答: {"error":...}
```

| 症状 | 確認すること |
| --- | --- |
| 記事キーを読み取れない | URL の形。`https://note.com/<ユーザー>/n/<記事キー>` になっているか |
| HTTP 404 | 記事が公開されているか。ブラウザで同じ URL を開けるか |
| 通信に失敗する | ネットワーク・プロキシの設定。`--fetch-timeout` を延ばす |
| 画像だけ失敗する | メッセージに何枚目のどの URL かが出ます。その URL をブラウザで開けるか |
| 本文が思ったものと違う | `--dump-article` で、何をどう取り込んだかを確認する |

終了コードは、成功 0 / 引数の誤り(URL の形など)2 / 出力先に既存 3 / 取得・解析の失敗 4 です。

## スライド画像への変換(note2slides-images)

資料の各スライドを、1 枚ずつ画像として書き出します。後続の動画生成はこの画像を並べて使います。

```bash
.venv/Scripts/python.exe -m note2slides.images_cli build/sample.pptx -o build/slides
```

```
build/slides/
  slide_001.png   1920x1080 / RGB(アルファなし)
  slide_002.png
  ...
  slides.json     スライドの順番と枚数の一覧
```

* ファイル名は 1 起点の連番なので、辞書順とスライド順が一致します。
* 全スライドが同じ画素数で出ます(動画のフレームサイズをそろえるため)。
* 元が 16:9 でない資料は、引き伸ばさずに背景色の余白を足して合わせます。
* ffmpeg から使う場合は `slide_%03d.png` で読み込めます。

変換は **LibreOffice(ヘッドレス)で PDF にしてから、PDF を目的の解像度で描画** します。
PowerPoint は不要です。PDF を経由するので、拡大しても文字や図形が劣化しません。
資料の代わりに PDF を直接入力することもできます(その場合 LibreOffice は不要)。

主なオプション:

| オプション | 説明 |
| --- | --- |
| `-o, --outdir` | 出力先(既定は入力と同じ場所の `<名前>_slides`) |
| `-f, --force` | 出力先に既に画像がある場合に上書きする(古い連番は削除する) |
| `--width` / `--height` | 画像サイズ(既定は 1920、高さは 16:9 で自動計算) |
| `--format` | `png`(既定)または `jpg` |
| `--prefix` / `--digits` | ファイル名の接頭辞と連番の桁数 |
| `--keep-pdf` | 中間生成物の PDF を残す |
| `--contact-sheet` | スライドを並べた一覧(`contact_001.png` …)も作る |
| `--contact-columns` / `--contact-rows` | 一覧の列数・行数(既定 4 x 3 = 12 枚) |
| `--soffice` | LibreOffice の場所(既定: 自動検出、環境変数 `SOFFICE_PATH` でも指定可) |
| `--timeout` | LibreOffice の待ち時間(秒、既定 180) |
| `--check` | 変換に必要な外部ツールの状態だけを表示する |

### 見比べるための一覧(`--contact-sheet`)

読みには「合成する前に何と読まれるかを確かめる」手立てがあります
(→ [読み方の下読み](#読み方の下読みnote2slides-reading))。**絵にはありません。**
何が正しい絵かを決められないので、自動では判定できないからです。確かめる方法は
**全部を画像にして目で見る** しかありません。

`--contact-sheet` は、そのための並べ方だけを引き受けます(**判定はしません**)。

```bash
.venv/Scripts/python.exe -m note2slides.images_cli build/sample.pptx \
    -o build/slides --contact-sheet
```

```
build/slides/
  slide_001.png ... slide_044.png
  contact_001.png   12 枚ずつ並べた一覧(44 枚なら 4 枚になる)
  ...
```

1 枚ずつ開くと 44 回開くことになり、**そもそも見ないほうへ倒れます。** 並べてしまえば、
場所が余りすぎている画面・文字が帯に重なっている画面・1 枚だけ極端に小さい画面は、
**隣と比べたときにいちばん見つかります。** 番号を必ず添えるので、見つけたものを
「3 枚目の図解が小さい」と指させます。

### 変換に失敗したとき

まず外部ツールの状態を確認します。

```bash
.venv/Scripts/python.exe -m note2slides.images_cli --check
```

失敗時のメッセージには、実行した LibreOffice のコマンド・終了コード・出力がそのまま載ります。
同じコマンドを手元で実行すれば、同じ失敗を再現できます。

| 症状 | 確認すること |
| --- | --- |
| LibreOffice が見つからない | インストール状況。`--soffice` か `SOFFICE_PATH` でパスを指定する |
| LibreOffice が何も出力しない | 他の LibreOffice が起動中でないか(変換専用のプロファイルを使いますが、環境によっては影響します) |
| 時間切れになる | 資料の枚数や画像の重さ。`--timeout` を延ばす |
| 枚数が合わない(警告が出る) | 非表示スライドの有無 |
| 文字化け・フォントが違う | 変換した環境にそのフォントが入っているか(LibreOffice は代替フォントで描画します) |

終了コードは、成功 0 / 引数の誤り 2 / 出力先に既存 3 / 変換失敗 4 / LibreOffice なし 5 です。

## ナレーション音声への変換(note2slides-audio)

資料からスライド 1 枚ごとのナレーション音声(WAV)を書き出します。

```bash
.venv/Scripts/python.exe -m note2slides.audio_cli build/sample.pptx -o build/audio
```

```
build/audio/
  narration_001.wav   スライド 1 枚目のナレーション
  narration_002.wav
  ...
  narration.json      スライド番号・長さ・読み上げた文章・音量の一覧
```

* ファイル名の番号はスライド番号です。`slide_001.png` と `narration_001.wav` が対になります。
* 読み上げる文章が無いスライド(コードや表だけのスライドなど)も、番号がずれないように無音の WAV を出します。
* 全ファイルを **48000Hz / 16bit / モノラル** に揃えて出します。
* `narration.json` には 1 本ごとの長さが入っています。スライドを何秒映すかは、この長さから決められます。
* あわせて、読み上げた単位(文・行)とその後ろの間、前後の無音も入れています。動画を作るときの
  字幕は、これと長さから「どの文が何秒目か」を割り出します(→ [字幕と章立て](#字幕と章立て))。

### 音声合成の方式

| エンジン | 中身 | 用途 |
| --- | --- | --- |
| `voicevox-nemo` | [VOICEVOX Nemo](https://voicevox.hiroshiba.jp/nemo/) ENGINE | **標準**。人格を持たない声(女声1〜6 / 男声1〜3) |
| `voicevox` | [VOICEVOX](https://voicevox.hiroshiba.jp/) ENGINE | Nemo が入っていない場合。ニューラル音声合成で、長く聞いても違和感が少ない |
| `onecore` | Windows.Media.SpeechSynthesis | VOICEVOX が無い環境向け。16000Hz 固定 |
| `sapi` | System.Speech | 同上。出力形式を指定できる |

既定は `auto` で、この順に使えるものを選びます。どれも手元で動き、通信も従量課金もありません。

VOICEVOX と VOICEVOX Nemo は同じ API を話す別のエンジンで、扱いも同じです
(接続先のポート・`run.exe` の場所・公開時のクレジット表記だけが違います)。
どちらも、起動していればそこに接続し、起動していなければ `run.exe` を探して起動します
(自分で起動した場合だけ、終了時に止めます)。開いている VOICEVOX アプリには触れません。
接続先は `--voicevox-url` / `VOICEVOX_URL`、Nemo は `VOICEVOX_NEMO_URL` で指定できます。

音声は「話者/スタイル」で指定します(`--voice "男声3/ノーマル"`)。
指定しない場合は標準のナレーション音声(下記)を使います。使える音声は `--list-voices` で確認できます。

### 標準のナレーション音声

**VOICEVOX Nemo の「男声3 / ノーマル」** を標準にしています。
`--engine` も `--voice` も指定しなければこの声になり、音声・動画のどちらのコマンドでも同じです。

```bash
# 標準の声で作る(指定は要りません)
.venv/Scripts/python.exe -m note2slides.video_cli build/sample.pptx -o build/sample.mp4
```

使える声を全部測って絞り込み、残った候補を実際に通しで聞いたうえで決めています
(→ [note2slides-voices](#ナレーション音声の聴き比べnote2slides-voices))。この声にした理由です。

| 観点 | この声の位置 |
| --- | --- |
| 高さ | 128Hz。候補の中で最も低い部類で、耳に刺さらず、音量を上げなくても聞き取れる |
| 抑揚 | 2.90 半音。演技寄りではなく、声より内容に注意が向く |
| 速さ | 8.68 モーラ/秒。標準の速さ(1.0 倍)のままで聞き取れる |
| 人格 | 特定のキャラクターではないため、聞き手が思い浮かべる人物像や作品が無い |
| 表示 | 公開時のクレジットが `VOICEVOX Nemo` だけで済み、動画にキャラクター名が出ない |

読み上げ設定(速さ・高さ・抑揚・音量)と、スライドごとの間は変えていません。
Gen7 までに決めた既定値をそのまま使います
(動画の頭の無音だけ、最初の一言を聞き逃さないように別に決めています →
[聞きやすさのために行っていること](#聞きやすさのために行っていること))。

VOICEVOX Nemo が入っていない環境では、`auto` が VOICEVOX の「No.7 / アナウンス」に下がります
(Gen7 まで標準にしていた声です)。声は変わりますが、生成の手順と結果の形式は同じです。

別の声を 1 回だけ試す場合は `--engine` と `--voice` を指定します。

```bash
.venv/Scripts/python.exe -m note2slides.audio_cli build/sample.pptx -o build/audio \
    --engine voicevox --voice "No.7/アナウンス"
```

標準そのものを変える場合は [決めたあとにすること](#決めたあとにすること) を参照してください。

> **公開時のクレジット**
> VOICEVOX で作った音声を含む動画を公開する場合、キャラクター名の表示(例: `VOICEVOX:No.7`)が必要です。
> 標準の声(VOICEVOX Nemo)は話者名を出さず、`VOICEVOX Nemo` と表示すれば足ります。
> 使った音声に対応する表記は `narration.json` の `credit` に入っています。

### 聞きやすさのために行っていること

「文章を音声にできる」ことと「動画のナレーションとして聞ける」ことは別なので、次の 4 つを合成の前後で行っています。

**1. 間の長さをこちらで決め、1 枚分をひと続きに読ませる**

合成エンジンに任せると文の切れ目が詰まって早口に聞こえるため、文・行の単位に区切って
間の長さをこちらで決めます。

| オプション | 間の位置 | 既定 |
| --- | --- | --- |
| `--sentence-pause` | 文と文の間 | 0.35 秒 |
| `--line-pause` | 行(段落・箇条書きの項目)の間 | 0.6 秒 |
| `--lead-silence` | スライドが変わってから話し始めるまで | 0.3 秒 |
| `--opening-silence` | **最初のスライド** で話し始めるまで | 1.0 秒 |
| `--tail-silence` | 話し終わってから次のスライドまで | 0.7 秒 |
| `--max-chars` | この長さを超える文は読点で区切る | 100 文字 |

ただし、区切りごとに合成を分けて音声をつなぐことはしません。合成エンジンは渡された文字列を
1 つの発話として扱い、その書き出しの音程を高く取ります。分けて頼むと、文や箇条書きの項目が
切り替わるたびに書き出しの音程が現れ、そこだけ音程と抑揚が跳ね上がって聞こえます。

そこで、1 枚分は区切りと間を添えてまとめて渡し、間も読み上げの中に置いてもらいます。
こうすると間は保ったまま、1 枚が地続きの読み方になります。実際に、上の例の
「記事を見出しごとに分割する」の書き出しは 388Hz から 227Hz になり、前の文の読み終わりから
続けて読んだ高さに収まります。

| エンジン | 間の入れ方 |
| --- | --- |
| voicevox | 読みをつないでから音程を決め直し、間を無音の拍(`pause_mora`)として入れる |
| sapi / onecore | SSML の `<break>` として入れる(SSML を扱えない音声では間なしに戻します) |

合成エンジンが付ける前後の余白は長さがまちまちなので、削ってから `--lead-silence` /
`--tail-silence` を入れ直します。間の長さはスライドごとにばらつきません。

**4. 最初の一言が聞き取れるようにする**

動画の 1 音目は、聞き逃しても前後の文脈から補えません。ここだけは次の 2 つを行っています。

*余白を付けて合成させる。* VOICEVOX は前後の余白も含めて 1 本の波形を作ります。余白を 0 で
頼むと、最初の拍が「無音から立ち上がる」条件で作られ、本来の大きさになるまで 70 ミリ秒ほど
かかります。拍の長さは 0.1 秒前後なので、これでは 1 音目がほとんど聞こえません
(最後の拍も、消え際が途中で終わります)。そこで余白を付けて作らせ、上記のとおり削ってから
間を入れ直します。**余白は捨てるので、読み上げの長さも間も変わりません。**
変わるのは前後の拍の作られ方だけです。

```
余白なし  [いー]ラーニング…    <- 「い」の頭が痩せ、削られて消える
余白あり  ..[イー]ラーニング…  <- 余白の中で立ち上がり、拍が丸ごと残る
```

*動画の頭は間を長く取る。* 再生が始まった直後は、視聴者はまだ画面を見ておらず、再生する
側も音を出し始めたところです。途中のスライドと同じ 0.3 秒で話し始めると最初の一言を
聞き逃すため、最初のスライドだけ `--opening-silence`(既定 1.0 秒)まで延ばします。
2 枚目以降は前のスライドの `--tail-silence` が前にあるので、この問題は起きません。

**2. 読み上げに向かない文字を落とす**

| すること | 理由 |
| --- | --- |
| 全角英数などの表記をそろえる | `ＡＩ` と `AI` で読みが変わらないようにする |
| 行頭の箇条書き記号(`・` `-` `*` `#`)を落とす | 画面には出ているが、読み上げる文字ではない |
| 絵文字・矢印・罫線を落とす | 読み上げても音にならない(伏せ字の `○` は残します。落とすと「最大○万」が「最大万」になるため) |
| URL を落とす(`--read-urls` で読ませられる) | 1 文字ずつ読まれて意味が取れない |
| 日本語の間に入った空白を詰める | `1 枚` が「いち……まい」と間を空けて読まれてしまう |
| 句点が無い行に句点を補う | 無いと語尾が上がったまま次の行に続いて聞こえる |
| 読み方辞書(`--dict`)で置き換える | 固有名詞や英単語の読み間違いを直す |

空白を詰めるのは、記事では `1 枚` `30 秒` `Markdown 記事` のように数字や英単語と日本語の間に
空白を入れて書くことがあり、合成エンジンがそこを語の切れ目とみなすためです。空白は表記上のもので、
詰めても意味は変わりません(画面には元の表記がそのまま出ます)。
英数字どうしの空白は語の区切りなので残します(`note2slides article.md` は 2 語のまま読みます)。
記号の隣の空白も、詰めると読み方が変わることがあるため残します(`1. 四つ目`)。

句点を補う以外はすべて文字を減らすだけで、元の記事に無い内容は足しません。
実際に合成へ渡した文字列は `narration.json` の `reading` に、落とした・補った内容は `notes` に入ります。

読み方辞書は `{"表記": "よみ"}` の形の JSON です。

```json
{ "note": "ノート", "TTS": "ティーティーエス" }
```

**3. 全ファイルの音量を YouTube の基準にそろえる**

音量が上下すると、長時間聞いたときに疲れます。全ファイルを 1 本の動画として
[ITU-R BS.1770-4](https://www.itu.int/rec/R-REC-BS.1770/) で測り、**同じ補正値** を全ファイルにかけます
(ファイルごとにそろえると、静かなスライドだけが持ち上がって、スライドが変わるたびに音量が動いて聞こえます)。

既定の目標は **-16 LUFS** です。YouTube は約 -14 LUFS を基準に音量をそろえるので、
あとから BGM を足す余地を 2dB 残しています。

合成音声は平均に対してピークだけが 15dB ほど飛び出すため、目標まで持ち上げるとピークが振り切れます。
全体を下げると今度は音量が足りないので、**飛び出したところだけ** を滑らかに抑えます(`--peak-ceiling`、既定 -1.5 dBFS)。
実際にどうなったかは `narration.json` の `loudness` に入ります。

```json
"loudness": { "gain_db": 6.56, "measured_lufs": -22.56, "result_lufs": -16.21,
              "result_peak_dbfs": -1.5, "limited": true, "limit_db": 5.02 }
```

`--no-loudness` を付けると、この調整をせず合成したままの音量で出します。

### 何を読み上げるか

読み上げる文章は、資料に書かれている文字をそのまま使います。要約・言い換え・補足の生成は行いません。
表・コード・図のように、画面には出ていても文字として読み上げられないものだけ、
画面に出ている文字を使って案内文を組み立てます(後述)。
スライドごとに、次の順で読み上げ元を選びます。選んだ結果は `narration.json` の `source` に入ります。

| source | 読み上げ元 |
| --- | --- |
| `notes` | 発表者ノート(教材シナリオのナレーション、または note2slides が入れた記事の本文) |
| `screen` | 画面に出ている表・コード・図の案内(ノートが無い場合) |
| `body` | スライドのタイトルと本文(表・コード・図が無い場合) |
| `title` | スライドのタイトルだけ(本文が無い場合) |
| `none` | 読み上げる文字が無い(無音になる) |

タイトルに付く「（続き）」は画面上の目印なので、読み上げからは外します。
同じ見出しが続くスライドでは見出しを読み直しません(前のスライドで読み上げているため)。

ノートに指示行(`[note2slides] ...`)がある場合は、そこに読み上げる内容が決まっているものと
して扱います。文章が無ければ `none`(無音)にし、画面の案内文で埋めません。
教材シナリオで「ここは読み上げない」と決めた画面がこれにあたります。

### 画面に出ているものの案内(表・コード・図)

表・コード・図は、画面には出ていますが、そのままでは読み上げる文字になりません。
何も言わずに映すと、視聴者は何を見ればよいのか分からないまま次のスライドへ進んでしまいます。
そこで、**画面に出ている文字だけ** を使って案内文を組み立てます(`guidance.py`)。

**表** は、列の見出しと各行を組み合わせて、行ごとに読みます。視聴者が読み上げを聞きながら
画面のどの行を見ればよいか分かるよう、行の呼び名には左端のセルを使います。

```
画面の表をご覧ください。
列は左から、工程、入力、出力です。
資料生成の行は、入力が Markdown 記事、出力がプレゼンテーションです。
画像化の行は、入力がプレゼンテーション、出力がスライド画像です。
```

**コード** は読み上げません(1 文字ずつ読まれても聞き取れないため)。何がどれだけ出ているかを
伝えて画面へ導き、日本語で書かれたコメント(書き手が読み手に向けて書いた文)だけを読みます。
シェルのコードブロック(`bash` など)は「コード」ではなく「コマンド」と呼びます。

```
画面のコマンドをご覧ください。
```

**図** は「画面の図をご覧ください」と案内し、画面に説明(キャプション)が出ていればそれを読みます。
図の内容そのものは説明しません(見て分からない絵は補えないため)。

いずれも、記事に無い事実や意味は足しません。表の中身を並べ替えたりまとめたり、
そこから言えることを付け加えたりもしません。案内文が不要な場合は、資料の発表者ノートに
文章を書いてください(ノートがあればノートを優先して読みます)。

### 画面を読む時間(`hold`)

コードや図は、読み上げを聞くだけでは足りず、画面を読む時間が要ります。
そのため読み終わったあとに無音を置き、そのぶんスライドを長く映します(コードは行数に比例、最大 6 秒)。
この時間は原稿(`script.json`)の `hold` に秒で入っていて、手で変えられます。

```json
{ "index": 8, "title": "変換を自動化する（続き）", "source": "screen",
  "text": "画面のコマンドをご覧ください。", "hold": 1.0 }
```

教材シナリオの `見る時間` もここに入ります。読み上げる文章が無いスライドでは、`hold` が
そのままそのスライドを映す長さになります(`hold` が無い場合は `--silence` の既定 2 秒)。

### 読み方を直したいとき

まず **何と読まれるかを見ます**(`note2slides-reading`。音は作らないので数秒です)。
語の読み方だけを直すなら読み方辞書が手軽です。

```bash
.venv/Scripts/python.exe -m note2slides.reading_cli build/sample.pptx --dump-dict readings.json
# readings.json の「よみ」を直す
.venv/Scripts/python.exe -m note2slides.audio_cli build/sample.pptx -o build/audio -f --dict readings.json
```

合成したあとで確かめる場合は、`narration.json` の `reading`(合成に渡した文字列)と
`latin_readings`(英字が何と読まれたか)を見ます。

文章そのものを変えたい場合は、原稿を書き出して直し、その原稿を入力にして合成します。
資料を作り直す必要はありません。

```bash
# 1. 原稿を書き出す
.venv/Scripts/python.exe -m note2slides.audio_cli build/sample.pptx -o build/audio --script-only

# 2. build/audio/script.json の text を編集する

# 3. 原稿から音声を作る
.venv/Scripts/python.exe -m note2slides.audio_cli build/audio/script.json -o build/audio -f
```

`index` はスライド番号です。1 からの連番になっていない原稿は、対応がずれるため受け付けません。

### 生成に失敗したとき

まず環境の状態を確認します。

```bash
.venv/Scripts/python.exe -m note2slides.audio_cli --check
```

失敗時のメッセージには、失敗したスライド番号・エンジンからのエラー(HTTP の応答内容を含む)・
再実行できるコマンドが載ります。合成に渡した内容と途中までの WAV は作業ディレクトリに残すので、
同じ要求を手元で送り直せます。

| 症状 | 確認すること |
| --- | --- |
| VOICEVOX が見つからない | インストール状況。`--voicevox-exe` か `VOICEVOX_ENGINE_PATH` で場所を指定する |
| VOICEVOX に接続できない | 別のポートで動いていないか。`--voicevox-url` か `VOICEVOX_URL` で指定する |
| 起動が時間切れになる | 初回は音声モデルの読み込みに時間がかかる。`--voicevox-startup-timeout` を延ばす |
| 日本語の音声が無いと言われる | Windows の設定 > 時刻と言語 > 言語と地域 から日本語の音声を追加する |
| PowerShell が見つからない | `--powershell` か環境変数 `POWERSHELL_PATH` で場所を指定する |
| 一部のスライドだけ失敗する | そのスライドの原稿(`--dump-script` で確認)。特殊な記号が含まれていないか |
| 時間切れになる | 原稿の量。`--timeout` を延ばす |
| 読み方が違う | `note2slides-reading` で読みを表示し、`--dict` か原稿で直す(上記) |
| 音量が小さい・大きい | `narration.json` の `loudness`。`--loudness` で目標を変える |

終了コードは、成功 0 / 引数の誤り 2 / 出力先に既存 3 / 合成失敗 4 / 音声合成が使えない 5 です。

## 読み方の下読み(note2slides-reading)

音声・字幕・動画は、**読み違えたままでも同じように生成できます**。終了コードは 0 で、
ファイルの数も長さも正しく、読み違いに気付くには最後まで聞くしかありません。
20 分の動画で 1 語の読み違いを見つけるには 20 分かかります。

このコマンドは、合成する前に **何と読まれるか** を仮名で取り出します。音を作らないので、
44 枚の資料でも数秒です。

```bash
.venv/Scripts/python.exe -m note2slides.reading_cli build/sample.pptx
```

```
原稿と読み
============================================================

[31]
  手元で全体を見たい方は、元の記事のコードを参照してください。
    テモトデゼンタイオミタイホオワモトノキジノコオドオサンショオシテクダサイ

英字の読み
============================================================
合成エンジンは英語の辞書を持たないため、英字はここだけが危ない。
  status -> スタタス(18枚目、29枚目、34枚目、35枚目)
  SUCCEEDED -> エスユウシイシイイイイイディイイイディイ ← 1文字ずつ読まれています(16枚目、…)

要確認
============================================================
  SUCCEEDED -> エスユウシイシイイイイイディイイイディイ ← 1文字ずつ読まれています(16枚目、…)
```

**正しい読みが何かは、機械には決められません。** 「方」は文脈によって「ほう」とも
「かた」とも読み、どちらが正しいかは書いた人にしか分かりません。読みを機械が決めれば、
原稿に無いことを足すことになります(要約・言い換えを生成しないのと同じ線です)。

そのためこのコマンドが返すのは次の 3 つで、直すかどうかは書いた人が決めます。

| 出るもの | 使い方 |
| --- | --- |
| 読み上げ単位ごとの **原稿と仮名** | 読み違いが *読んで* 分かる。全部に目を通す必要はない(下の 2 つが場所を教える) |
| 英字の語ごとの **仮名** | 合成エンジンは英語の辞書を持たずローマ字として読むため、英字はほぼここだけが危ない |
| **読みが分かれる語** | 「値」「通って」のように、日本語として複数の読みを持つ表記だけを挙げる |

**機械が「間違い」と言い切れるのは 1 つだけ** ——「英字が 1 文字ずつ読まれている」ことです。
`SUCCEEDED` が「エスユウシイ…」と読まれるのは、どんな原稿でも意図した読みではありません。
`AI` `MCP` のような略語は 1 文字ずつが正しい読みなので、**4 文字以上** のものだけを挙げます
(`PASS` `WARN` `FAIL` `JSON` `SUCCEEDED` がこれにあたります)。
A-Z の読みは表に書き写さず、**エンジンに聞いて** 作ります(エンジンの版が変わっても判定がずれないため)。

#### 読みが分かれる語

英字を絞り込んでも、**日本語の読み違いは残ります。**「値」を「ね」、「通っている」を
「かよっている」と読まれても、原稿の仮名を最後まで読まなければ気付きません。
44 枚ぶんの仮名を漏れなく追うのは、実際にはできません。

ここで言い切れるのは、正しい読みではなく **読みが分かれること** です。「方」を「ほう」と
読むか「かた」と読むかは書いた人にしか決められませんが、「この語は 2 通りに読まれる」ことは
原稿と関係なく言えます。そこで **分かれる語だけを名指しして、どちらで読まれたかを添えます。**

```
読みが分かれる語
============================================================
  方 -> カタ(ほかに ホオ とも読む語)(1枚目、4枚目、9枚目、…)
  方 -> ホオ(ほかに カタ とも読む語)(28枚目)
  値 -> ネ(ほかに アタイ とも読む語)(31枚目)
  通って -> カヨッテ(ほかに トオッテ とも読む語)(17枚目、35枚目)
```

* **同じ表記でも、読みが違えば分けて挙げます。**「進め方」はカタ、「古い方法」はホオで、
  どちらも正しい。まとめると両方の音が現れて「特定できません」にしかなりません。
* 1 つの表記につき 1 行です。「方」が 12 回出ても、確かめるのは **1 行** です。
* 候補の仮名は表に書き写さず、**エンジンに聞いて** 突き合わせます(英字と同じ理由)。
* 「何」「数」「間」のように候補の仮名が短く、文中の別の語にもそのまま現れる表記は
  **挙げません。** 見分けが付かないものを挙げると、毎回「特定できません」が並んで
  一覧そのものが読まれなくなります。

**これは合成前に書いた人が使うものです。** 原稿を書いた人(または AI)は、どちらのつもりで
書いたかを知っています。**知っている側が直すほうが、あとから聞いて探すより確実です。**

### 直す

読み方辞書(`{"表記": "よみ"}` の JSON)を書いて `--dict` に渡します。雛形を書き出せます。

```bash
.venv/Scripts/python.exe -m note2slides.reading_cli build/sample.pptx --dump-dict readings.json
# readings.json の「よみ」を直す(値は今の読みなので、そのままでは直りません)
.venv/Scripts/python.exe -m note2slides.reading_cli build/sample.pptx --dict readings.json
```

置き換えは文字列そのままなので、語だけでなく **文脈ごと** 書けます。長い表記から先に
置き換えるので、`Execution` と `GetExecutionHistory` を両方書いても混ざりません。

```json
{
  "SUCCEEDED": "サクシーデッド",
  "status": "ステータス",
  "見たい方は": "見たいかたは"
}
```

辞書は題材をまたいで使い回せます(`status` `json` のような語は、どの題材でも同じように読まれます)。

### 音声を作るときにも知らせる

`note2slides-audio` / `note2slides-video` は、**合成の前に** 同じ確認をして警告を出します
(語の数だけ問い合わせるので、数秒しか増えません)。読みを返せるのは VOICEVOX だけなので、
Windows 標準の音声合成では何もしません。

```
警告: 英字 2 件が 1 文字ずつ読まれています: SUCCEEDED(エスユウシイ…)、PASS(ピイエエエスエス)。
      意図した読みでなければ --dict で読み方を指定してください。
```

英字が何と読まれたかは `narration.json` の `latin_readings` にも残るので、
あとから聞き直さずに確かめられます。

### 主なオプション

| オプション | 説明 |
| --- | --- |
| `--words` | 英字の語だけを調べる(読み上げ単位ごとの仮名を出さない。速い) |
| `--dict` | 読み方辞書(JSON)。直した結果を確かめる |
| `--dump-dict` | 1 文字ずつ読まれている語だけを並べた辞書の雛形を書き出す |
| `-o, --out` | 結果を JSON として書き出す |
| `--voice` / `--engine` | 読みを聞く話者・エンジン(既定は音声生成と同じ) |

終了コードは、1 文字ずつ読まれている語が無ければ 0、あれば 6 です
(気付かずに公開しないための合図として、成功と分けています)。

## ナレーション音声の聴き比べ(note2slides-voices)

どの声を標準のナレーションにするかは、聞いた人にしか決められません。合成できることと、
30 分の教材を最後まで聞けることは別だからです。このコマンドは **決めるための材料** を作ります。

```bash
.venv/Scripts/python.exe -m note2slides.voice_compare_cli samples/narration_sample.md -o build/voice_compare
```

```
build/voice_compare/
  preview.wav              候補の冒頭を並べたもの(声の違いを直接比べる)
  compare.md               候補・設定・選んだ理由(まずこれを読む)
  compare.json             同じ内容の一覧(直して再実行できる)
  source.pptx              全候補が読み上げた資料
  no7-announce/
    continuous.wav         全スライドを続けて聞ける通し音声
    narration_001.wav ...  スライドごとの音声(動画に使うものと同じ)
    narration.json         使った話者・スタイル・読み上げ設定・音量
  no7-calm/
  ...
```

**聞く順番は 2 段階です。** まず `preview.wav`(サンプル記事・候補 6 つで約 3 分)で
候補の冒頭が続けて流れるので、声の違いはここで分かります。
そのうえで気になった候補の `continuous.wav`(1 候補あたり約 8 分)を通して聞きます。
第一印象では良く聞こえた声が、数分続けると疲れることがあるためです。
`preview.wav` のどこで候補が切り替わるかは `compare.md` に時刻で載せています。

### 何をそろえているか

候補どうしを比べられるように、声と読み上げ設定 **以外** はすべて同じにします。

| そろえるもの | 内容 |
| --- | --- |
| 原稿 | 同じ資料を全候補が読む(`source.pptx`) |
| 間・読み方の整形 | `note2slides-audio` と同じ処理をそのまま使う |
| 音量 | 候補ごとに全スライドをまとめて -16 LUFS へそろえる |
| 出力形式 | WAV 48000Hz / 16bit / モノラル |

音量をそろえるのは、大きいほうが良く聞こえてしまうためです。候補ごとに(候補内の全スライドを
まとめて)そろえるので、候補間の音量差は残りません。

入力には記事(.md)・資料(.pptx)・原稿(.json)のどれでも渡せます。記事を渡した場合は
1 回だけ資料に変換し、全候補が同じ資料を読みます。

### 候補の絞り込み(`--survey`)

VOICEVOX と VOICEVOX Nemo を合わせると 136 種類の声があります。全部を聴き比べるのは
できないので、**まず測って絞ります**。同じ文を全部の声に読ませ、長時間のeラーニングで
効いてくる 3 つを測ります(合成はしないので数分で終わります)。

```bash
.venv/Scripts/python.exe -m note2slides.voice_compare_cli --survey -o build/voice_survey
```

| 測るもの | 意味 | 長時間での見方 |
| --- | --- | --- |
| 高さ | 基本周波数(Hz) | 高いほど耳に付きやすく、聞き続けると疲れやすい |
| 抑揚 | 高さの振れ幅(半音) | 大きいほど演技寄りで、内容より声に注意が向く |
| 速さ | モーラ/秒 | 同じ倍率でも話者ごとに元の速さが違う |

読み(アクセント句)を作って長さと音程を決めるところまでは合成と同じ手順なので、
ここで測った値は実際に聞こえる音声のものと一致します。

`survey.md` には全部の声の測定値と、次の条件に入る 20 種類が載ります。
**人気や知名度ではなく、測った値で候補を絞る** ためのものです。

* 高さ 100〜260 Hz / 抑揚 3 半音以下 / 速さ 6.5〜9 モーラ/秒
* 話者ごとに既定のスタイル(感情や演技のスタイルは外す。読み上げ用のスタイルは残す)

条件は `voice_survey.py` の `DEFAULT_SCREEN` にあります。声質・語尾・息づかいは測れないので、
ここで残ったものを人が聞いて決めます。

### 候補と、その候補にした理由

組み込みの候補は `--list-candidates` で確認できます(音声は作りません)。

```bash
.venv/Scripts/python.exe -m note2slides.voice_compare_cli --list-candidates
```

絞り込みに残った 20 種類から、次の観点で 6 つを選んでいます。

1. 30 分聞いても疲れないか(高さが低め・抑揚が過剰でない)
2. 声ではなく内容に注意が向くか(キャラクター性・演技の強さが弱い)
3. 視聴者を選ばないか(特定の層にだけ強く好かれる声になっていないか)
4. 比較として意味があるか(基準との違いが 1 つに絞れているか)

4 のために、候補は「基準と何を変えたものか」が 1 つずつ違うようにしてあります。
同じ役割の候補を 2 つ入れても、聞く時間が倍になるだけで判断は増えません。

| 候補 | 話者/スタイル | エンジン | 位置づけ |
| --- | --- | --- | --- |
| `no7-announce` | No.7 / アナウンス | voicevox | Gen7 までの標準(比較の基準) |
| `no7-calm` | No.7 / アナウンス | voicevox | 同じ声を、速さ・抑揚・間で落ち着かせたもの |
| `nemo-female1` | 女声1 / ノーマル | voicevox-nemo | 人格を持たない声(基準と同じ声域) |
| **`nemo-male3`** | **男声3 / ノーマル** | voicevox-nemo | **聞いて選んだ現在の標準**(低い男性の声域) |
| `mitama-normal` | 暁記ミタマ / ノーマル | voicevox | 基準より低く、抑揚の小さい女性 |
| `rito-normal` | 離途 / ノーマル | voicevox | 最も低く、抑揚の小さい男性 |

VOICEVOX Nemo からは 2 つだけ入れています。Nemo の声は人格を持たず、公開時の表示も
話者名を含まない「VOICEVOX Nemo」で済むため、**キャラクターの声かどうか** という
一点だけを比べられる位置づけです。残り 7 声は、この 2 つと測定値が近いか、
速さ・抑揚が条件から外れるため入れていません。

一つ一つを候補にした理由は `voice_compare.py` の `CANDIDATES` に文章で書いてあり、
生成した `compare.md` にもそのまま入ります。**聞いた印象と、候補にした理由を突き合わせられます。**
候補に入れなかった声とその理由も `NOT_CHOSEN` に残してあり、`compare.md` に出ます。

候補を足したり外したりする場合は、`compare.json` を直して `--candidates` で渡します
(形式は同じなので、生成された結果をそのまま編集できます)。数を絞って聞き直す場合は `--only` です。

```bash
.venv/Scripts/python.exe -m note2slides.voice_compare_cli samples/narration_sample.md \
    -o build/voice_compare2 --only no7-announce,aoyama-normal
```

### 聴き比べに使う記事

`samples/narration_sample.md` は、この比較のために用意した記事です。実際のeラーニング動画で
起こる読み上げがひととおり出るようにしてあります(段落・入れ子の箇条書き・番号付きリスト・
引用・表の案内・コマンドの案内・英数字混じりの文・100 文字を超える文)。
別の記事を渡しても構いませんが、表やコードが 1 つも無い記事だと、案内文の読み上げを比べられません。

長さは 1 候補あたり約 8 分(スライド 25 枚)にしてあります。**第一印象と、聞き続けたときの
印象は違う** ので、数十秒では分からない疲れやすさを判断できる長さが要ります。
短く済ませたい場合は、短い記事を渡してください。

### 決めたあとにすること

このコマンドは標準の音声を **変更しません**。聞いて決めたあと、次を変更します。

| 変えるもの | 場所 |
| --- | --- |
| 標準の話者/スタイル | `src/note2slides/voicevox.py` の `VOICEVOX`(または `NEMO`)の `preferred_styles` の先頭 |
| 標準のエンジン | `src/note2slides/voicevox.py` の `EDITIONS` の並び順(auto がどちらを先に試すか) |
| 標準の速さ・抑揚・間 | `src/note2slides/audio_cli.py` の `--speed` / `--intonation` / `--sentence-pause` / `--line-pause` の既定値 |

1 回だけ試すなら、`--engine` と `--voice` で指定できます(動画生成でも同じです)。

この手順で決まったのが、現在の標準である
[VOICEVOX Nemo の「男声3 / ノーマル」](#標準のナレーション音声)です
(`nemo-male3`。エンジンの順と `preferred_styles` の先頭を変えただけで、
読み上げ設定は Gen7 までの既定値のままです)。

### 主なオプション

| オプション | 説明 |
| --- | --- |
| `-o, --outdir` | 出力先(既定: `build/voice_compare`) |
| `-f, --force` | 出力先に前回の結果がある場合に上書きする |
| `--survey` | 使える声をすべて測って一覧にする(音声は作らない) |
| `--candidates` | 候補の一覧(JSON。既定は組み込みの候補) |
| `--only` | 指定した id の候補だけで比較材料を作る |
| `--list-candidates` | 候補と選んだ理由を表示する(音声は作らない) |
| `--preview-seconds` | 頭出しに入れる長さ(秒、既定 30。0 で作らない) |
| `--loudness` / `--no-loudness` | 全候補でそろえる音量 |
| `--dict` | 読み方辞書(全候補で同じものを使う) |
| `--timeout` | 候補 1 つあたりの待ち時間(秒、既定 1800) |
| `--check` | 音声合成に必要な環境の状態だけを表示する |

### 生成に失敗したとき

候補の声が使えない場合は、**合成を始める前に** まとめて知らせます(候補 1 つで数分かかるため、
名前の間違いを最後まで待たずに済ませます)。使える音声は `note2slides-audio --list-voices` で確認できます。

合成そのものが失敗した場合は、その候補だけを失敗として記録し、**残りの候補は最後まで作ります**
(1 つ落ちても、残りで聴き比べは続けられます)。失敗した候補と原因は標準エラー出力に出るほか、
`compare.md` の「生成できなかった候補」と `compare.json` の `error` に残ります。

終了コードは、成功 0 / 引数の誤り 2 / 出力先に既存 3 / 一部または全部の候補が失敗 4 /
音声合成が使えない 5 です。

## 投稿用サムネイル(note2slides-thumb)

YouTube に投稿するとき、動画とは別にサムネイルの画像が要ります。資料と同じ描画・
同じ見た目で 1 枚絵を作るコマンドです。

```bash
# 教材シナリオから(表紙の題と副題をそのまま使う)
.venv/Scripts/python.exe -m note2slides.thumbnail_cli samples/lesson_scenario.md \
    -o build/lesson/thumbnail.png --label "第1回"

# 資料(.pptx)から
.venv/Scripts/python.exe -m note2slides.thumbnail_cli build/lesson/lesson.pptx \
    -o build/lesson/thumbnail.png

# 入力を使わず、文字だけを指定する
.venv/Scripts/python.exe -m note2slides.thumbnail_cli \
    --title "教材シナリオから動画を作る" --subtitle "note2slides" -o build/thumbnail.png
```

出力は既定で 1280x720(YouTube が推奨する 16:9)の PNG です。作り方はスライド画像と
同じで、1 枚だけの .pptx を PDF 経由で画像にするため、フォントの見え方も資料と同じに
なります(LibreOffice が必要です)。

題は、一覧で小さく表示されても読めるように、表紙より大きい文字にします。大きさは
固定ではなく、**語の途中で切らずに 2 行に収まる、いちばん大きい文字** を選びます
(2 行に収まらない場合だけ 3 行にします)。

3 行にも収まらない長い題は、**収まる大きさまで小さくしてから** 出します。題を切り詰める
ことはしません(書いていないものを出すことになるため)。ただし、そこまで小さくなった題は
一覧では読めないので、**警告で知らせます。**

```
警告: 題が長いため、一覧で読める大きさに収まりません(87 文字): AIにいきなり…
      短い題を --title で指定してください(動画の題とサムネイルの題は別にできます)。
```

| オプション | 説明 |
| --- | --- |
| `-o, --output` | 出力先(既定は入力と同じ場所の `<名前>_thumbnail.png`) |
| `--title` / `--subtitle` | 出す文字(既定は入力の表紙の題と副題) |
| `--no-subtitle` | 副題を出さない |
| `--label` | 左上に出す短い文字(例: `第23回`) |
| `--width` | 横の画素数(既定 1280) |
| `--format` | `png` / `jpg`(既定 png) |
| `--theme` | 見た目(資料と同じものを指定します) |
| `--keep-pptx` | 元にした 1 枚だけの .pptx も残す(PowerPoint で手直しする場合) |
| `--soffice` | LibreOffice の場所 |

サムネイルの文字は、動画の題と別にしたいことがあります(動画の題は説明的に、
サムネイルは短く、など)。その場合は `--title` / `--subtitle` で上書きしてください。
入力から取り出した文字を、こちらで言い換えたり要約したりはしません。

動画と一緒に作る場合は、動画コマンドに `--thumbnail` を付けても構いません
(資料から動画を作るときだけ使えます)。

```bash
.venv/Scripts/python.exe -m note2slides.video_cli build/lesson/lesson.pptx \
    -o build/lesson/lesson.mp4 --thumbnail --thumbnail-label "第1回"
```

## ナレーション付き動画(note2slides-video)

資料から、スライドごとにナレーションが付いた動画(MP4)を作ります。
スライド画像とナレーション音声も内部で書き出すので、資料があれば 1 コマンドで動画まで作れます。

```bash
.venv/Scripts/python.exe -m note2slides.video_cli build/sample.pptx -o build/sample.mp4
```

```
build/
  sample.mp4          動画本体
  sample_video.json   何秒目にどのスライドが出るかの一覧
  sample_slides/      途中で作ったスライド画像
  sample_audio/       途中で作ったナレーション音声
```

動画は **1920x1080 (16:9) / 30fps / H.264(yuv420p)+ AAC 48kHz ステレオ の MP4** です。
YouTube にそのまま投稿でき、一般的なプレイヤーでも再生できます。PowerPoint は使いません。

### スライドの切り替わりと音声のずれについて

「そのスライドのナレーションが終わるまで、そのスライドを映す」ようにしています。
音声と映像の長さが少しでも食い違うと、ずれが後ろのスライドへ積み重なり、最後には
別のスライドを読み上げているように見えてしまうため、長さは次の順で決めています。

1. 1 枚を映す長さを、その音声の長さ以上にする(切り上げるだけで、縮めません)
2. その長さをコマ単位に切り上げる(動画は 1/fps より細かい時刻を表せません)
3. 音声側にも無音を足して、2 で決めた長さちょうどにそろえる

そのため、ナレーションの途中でスライドが変わることも、音声が途中で切れることもありません。
実際に割り当てた時刻は `sample_video.json` に入っています。

```json
{ "index": 2, "image": "slide_002.png", "audio": "narration_002.wav",
  "start": 5.033, "at": "0:00:05.0", "duration": 20.7, "narration": 20.674 }
```

`at` の時刻をプレイヤーで開けば、そのスライドの先頭から確認できます。
`duration` と `narration` の差(この例では 0.026 秒)が、長さをそろえるために足した無音です。

動画の先頭 1 秒は無音です(1 枚目のスライドは出ています)。再生を始めた直後に話し始めると
最初の一言を聞き逃すためで、この無音も 1 枚目のナレーションに含まれています
(→ [最初の一言が聞き取れるようにする](#聞きやすさのために行っていること))。
そのため、ここでも映像と音声の長さの決め方は変わりません。

### 内容を確認して直すとき

動画をひととおり見て、読み方や見た目を直したくなった場合、**動画全体を作り直す必要はありません**。
`sample_slides/` と `sample_audio/` に素材が残っているので、直したい工程だけをやり直して、
素材から動画を組み立て直せます。

```bash
# 例: 読み方だけを直す(音声を作り直す)
.venv/Scripts/python.exe -m note2slides.audio_cli build/sample.pptx -o build/sample_audio -f --dict readings.json

# 素材から動画を組み立て直す(資料は指定しない)
.venv/Scripts/python.exe -m note2slides.video_cli --slides build/sample_slides --audio build/sample_audio \
    -o build/sample.mp4 -f
```

素材はスライド番号で対応付けます。枚数や番号が食い違う場合は、どの番号が足りないかを示して中断します
(気付かないまま、別のスライドを読み上げる動画ができるのを避けるため)。

### 字幕と章立て

動画と一緒に、投稿するときに使う 2 つのファイルも書き出します。

```
build/
  sample.mp4
  sample.srt             字幕(投稿時に添える)
  sample_chapters.txt    概要欄の先頭に貼る章立て
  sample_video.json      何秒目にどのスライドが出るか
```

字幕は動画に焼き込みません。別ファイルで渡すほうが、見る人が表示を切り替えられて、
あとから文字だけを直すこともできるためです。形式は `--captions vtt` で WebVTT に、
`--captions both` で両方、`--captions none` で作らないようにできます。

```
1
00:00:01,000 --> 00:00:07,234
この教材では、教材シナリオから、
ナレーション付きの動画を作る方法を説明します。
```

字幕は音声を聞き取り直して作るのではありません。**何を読み上げたか** は
`narration.json` に、**それが何秒目にあるか** は動画の時間割りに、それぞれ
すでにあります。この 2 つから組み立てるので、字幕の文字は読み上げた文章と必ず一致し、
聞き取りの誤りが入ることもありません。

1 枚の中のどこで字幕を切り替えるかは、次のように決めています。

```
音声の長さ - 前後の無音 - 文と文の間 = 読み上げに使われた時間
    この時間を、各文の「読み上げるのにかかる長さの目安」で按分する
```

目安は文字の種類から見積もった長さ(かな 1 文字 = 1、漢字 = 1.7、読点 = 6.5 など)で、
実際の合成結果とは少しずれます。**ずれはスライドの中だけ** で、各スライドの先頭で実測の
長さに合わせ直すため後ろへ積み上がりません。手元の VOICEVOX Nemo(男声3)で測ったところ、
ずれは平均 0.1 秒・最大 0.4 秒でした(`tests/test_captions_compat.py` で確認しています)。

読点の重みが大きいのは、読点そのものは音になりませんが、合成エンジンがそこで間を取るためです
(この分を数えないと、読点の多い文だけ字幕が 1 秒近く早く切り替わります)。

1 つの字幕は 2 行・1 行 24 文字までに収めます(`--caption-chars` で変更できます)。
長い文は読点で分け、行頭に句読点が来ないようにし、漢字と送り仮名の間では折り返しません。
文と文の間では字幕を消しません(間のたびに画面が点滅して読みにくいため)。

章立ては、スライドの見出しが変わるところを章の切れ目にして、概要欄にそのまま貼れる形で書き出します。

```
0:00 教材シナリオから動画を作る
0:14 この教材で学ぶこと
0:30 記事から作るときとの違い
```

YouTube は「最初の章が 0:00 から」「1 つの章が 10 秒以上」「3 つ以上ある」を満たしたときだけ
目次を表示します。最初の 2 つはこちらで満たします(10 秒に満たない章は前の章にまとめます)。
章の数が足りないときは、そのまま書き出したうえで警告します。

素材から組み立て直すとき(`--slides` / `--audio`)も同じように作ります。読み上げた文章は
`narration.json` から読むので、音声だけを作り直せば字幕もそれに追随します。手で並べた素材で
`narration.json` が無い場合は、字幕と章立てを作らずに動画だけを書き出します。

| オプション | 説明 |
| --- | --- |
| `-o, --output` | 出力する動画(既定は入力と同じ場所・同じ名前の .mp4) |

### 生成に失敗したとき

まず環境の状態を確認します(ffmpeg・LibreOffice・音声合成をまとめて表示します)。

```bash
.venv/Scripts/python.exe -m note2slides.video_cli --check
```

失敗時のメッセージには、実行した ffmpeg のコマンド・終了コード・出力がそのまま載ります。
ffmpeg への指示(どのスライドを何コマ映すか)とつないだ音声は作業ディレクトリに残すので、
同じコマンドを手元で実行すれば同じ失敗を再現できます。書きかけの動画は削除します
(完成したものと見分けが付かないため)。

| 症状 | 確認すること |
| --- | --- |
| ffmpeg が見つからない | `pip install -e .` を実行したか。`--ffmpeg` か `FFMPEG_PATH` で場所を指定する |
| libx264 / aac が使えないと言われる | ffmpeg のビルド。同梱のもの(`--ffmpeg` を指定しない)を使う |
| 画像と音声の対応が取れない | 同じ資料から書き出した素材か。片方だけ作り直していないか |
| スライド画像の大きさが揃っていない | 同じ条件で書き出した画像か(note2slides-images は揃えて出します) |
| 時間切れになる | 資料の長さ。`--timeout` を延ばす(1 時間の動画で数十分かかることがあります) |
| 動画の長さが合わないと警告が出る | `sample_video.json` の `duration` と実際の長さ。ナレーションが切れていないか |

終了コードは、成功 0 / 引数の誤り 2 / 出力先に既存 3 / 生成失敗 4 / 外部ツールが使えない 5 です。

## 開発

```bash
.venv/Scripts/python.exe -m pytest                # テスト(外部ツールが無い環境では該当分をスキップ)
.venv/Scripts/python.exe -m pytest -m "not slow"  # LibreOffice や音声合成を使うテストを除く
```

外部ツールを使うテストは、そのツールが無ければスキップします(VOICEVOX が無い環境でも `pytest` は通ります)。

### 出力の文字コード

各コマンドは、標準出力・標準エラー出力を **UTF-8** で書きます(`console.use_utf8_output`)。

Windows では、出力先がコンソールでないとき(パイプ・リダイレクト)、Python は locale の
符号化を使います。日本語環境では cp932 になり、2 つのことが起きます。

* cp932 に無い文字を出そうとすると `UnicodeEncodeError` で **落ちます**。note 記事の題や
  見出しに絵文字は珍しくないため、記事やシナリオは正しく読めているのに、その題を表示する
  ところでコマンドが終わり、資料が作られません。
* 出力を受け取る側(ログファイル・別のツール・このリポジトリを開発する AI)は UTF-8 として
  読むため、日本語が **化けます**。失敗の理由を詳しく出しても読む側に届きません。

どちらも変換の中身とは関係のない失敗なので、各コマンドの入口(引数を解析するより前)で
切り替えます。コンソールへ出す場合は Windows でも UTF-8 が使われるため、何も変わりません。

同じ理由で、`tests/conftest.py` は pytest 自身の出力も UTF-8 にします。このリポジトリの
テストは失敗の理由を日本語で書いているので、化けると失敗を見ても原因が分かりません。

処理の流れです。

```
markdown_reader : Markdown  -> Article(ブロック列)
note_source     : note URL  -> Article(記事 API から本文 HTML と画像を取り込む)
planner         : Article   -> Deck(スライド構成)
scenario        : 教材シナリオ -> Deck(書かれた画面とナレーションをそのまま構成にする)
renderer        : Deck      -> .pptx

soffice         : .pptx    -> PDF(LibreOffice をヘッドレスで呼ぶ)
slide_images    : PDF      -> slide_001.png ...(pypdfium2 で描画)

narration       : .pptx    -> ナレーション原稿(スライド 1 枚 = セリフ 1 本)
reading         : 原稿     -> 読み上げの区切り + 各区切りの後ろに置く間
pronunciation   : 読み上げの区切り -> 仮名(合成せずに「何と読まれるか」を見る)
speech          : 合成エンジンの共通の型(どの方式でも同じ扱いにする)
voicevox        : 1 枚分の区切りと間 -> WAV(VOICEVOX / VOICEVOX Nemo を HTTP で呼ぶ)
tts             : 1 枚分の区切りと間 -> WAV(speech.ps1 経由で Windows の音声合成を呼ぶ)
waveform        : WAV の読み書き・間を置いた連結・音量の測定(BS.1770)
audio           : 上記を束ねて narration_001.wav ... + narration.json
voice_survey    : 全部の声を測る(高さ・抑揚・速さ)-> 候補を絞る材料
voice_compare   : 同じ原稿を候補ごとに読ませる -> 聴き比べる音声 + 選定理由

ffmpeg          : ffmpeg の場所の解決・実行・進捗の読み取り
video           : 画像 + 音声 -> 時間の割り当て -> sample.mp4 + sample_video.json
captions        : 読み上げ単位 + 時間の割り当て -> sample.srt / sample_chapters.txt
```

レイアウトの調整は `src/note2slides/style.py`、画像の出力条件は `ImageOptions`、
音声の出力条件は `AudioOptions`(間の取り方は `ReadingStyle`)、動画の出力条件は `VideoOptions`
に集約しています。
外部コマンドの呼び出しで共通する部分(実行したコマンドと出力を失敗時に残す)は `proc.py` にあります。

入力の種類が増えても後段は変わりません。`markdown_reader` と `note_source` は
どちらも `Article` を返すところまでが仕事で、`note_source` は記事中の画像を
ローカルへ保存し、ブロックの参照先をそのファイルに書き換えます。そのため
planner から先は「手元の画像を参照している記事」と区別が付かず、資料・画像・
音声・動画の処理は 1 つも分岐しません。

教材シナリオも同じ形にしてあります。違うのは、記事が `Article`(文章の並び)を
経由して planner に構成を推測させるのに対し、シナリオは構成そのものなので
`scenario` が直接 `Deck` を返すところだけです。ナレーションは `Slide.notes` に
入れるので、`narration.py` は「ノートがあればそれを読む」という既定の動きの
ままシナリオの文章を読み上げます。

```
記事      : Markdown -> Article -> [推測] -> Deck
シナリオ  : Markdown ------------------->  Deck
```

文章では表せない指定(読み上げないこと・画面を見せる時間)だけは、ノートの
指示行(`narration.DIRECTIVE_PREFIX`)として資料に残します。資料を経由しても
指定が失われないので、資料から先の工程(画像・音声・動画)は 1 つも変わりません。

動画の同期は `video.py` の `build_timeline` だけで決まります。ここが「スライドを何秒映すか」と
「音声を何秒に合わせるか」の両方を返すので、映像と音声の長さが食い違うことがありません。
字幕もこの結果(`Segment`)から作るので、映像・音声・字幕の 3 つがずれることはありません。

字幕と章立ては、動画を書き出したあとに `captions.py` が組み立てます。必要なのは
「何を読み上げたか」と「それが何秒目か」だけなので、音声そのものは見ません。前者は
`narration.json` の `pieces`(読み上げ単位と間)と `lead_silence` / `tail_silence`、
後者は `Segment.start` です。1 枚の中で各文が何秒目かは、文字の種類から見積もった
長さで按分します(`captions.estimate_moras`)。見積もりの重みは実際の合成結果に
当てはめて決めており、`tests/test_captions_compat.py` が実物とのずれを測っています。

| 変えたいこと | 見る場所 |
| --- | --- |
| 字幕の行数・1 行の文字数・最短の表示時間 | `captions.py` の `CaptionStyle` |
| 読み上げの長さの見積もり(按分の重み) | `captions.py` の `_WEIGHT_*` |
| 章の切れ目と、まとめる短さの下限 | `captions.build_chapters` |

標準のナレーション音声は、この 2 つだけで決まります。同じ値を別の場所に持たないので、
実際に合成される声と説明が食い違うことがありません(`tts.default_narration()` がこの 2 つから
「エンジン名 / 話者・スタイル」を返し、聴き比べの `compare.md` もそれを使って現在の標準を書きます)。

| 決めているもの | 場所 |
| --- | --- |
| どのエンジンを最初に試すか | `voicevox.py` の `EDITIONS` の並び(先頭が `voicevox-nemo`) |
| そのエンジンが指定なしで選ぶ声 | `NEMO.preferred_styles` の先頭(`男声3/ノーマル`) |

音声の質に効く判断は次のように分かれています。どれを変えても他に影響しません。

| 変えたいこと | 見る場所 |
| --- | --- |
| 声そのもの(話者) | `voicevox.py` の `VOICEVOX` / `NEMO` の `preferred_styles` |
| 使えるエンジンと順番 | `voicevox.py` の `EDITIONS`(auto が試す順)と `Edition`(接続先・クレジット表記)、`tts.py` の `ENGINES` |
| 標準にする声を決める材料 | `voice_survey.py` の `DEFAULT_SCREEN`(測って絞る)、`voice_compare.py` の `CANDIDATES`(聴き比べ用の音声を作る) |
| 区切りと間、読み上げ用の整形 | `reading.py` |
| 読み違いの見つけ方(1 文字ずつ読まれている語) | `pronunciation.py` の `SPELLED_MIN_LETTERS` |
| 合成に頼むときの前後の余白(1 音目の出方) | `voicevox.py` の `SYNTH_PADDING` |
| 音量・形式 | `waveform.py`、`audio.py` の `DEFAULT_*` |

VOICEVOX と VOICEVOX Nemo の違いは `voicevox.py` の `Edition` に閉じています
(接続先のポート・`run.exe` の探し方・公開時のクレジット表記)。合成の手順は共通なので、
同じ API を話すエンジンが増えても `Edition` を 1 つ足すだけで済みます。

`speech.ps1` は **UTF-8 BOM 付き** で保存してください。Windows PowerShell 5.1 は BOM の無いファイルを cp932 として読むため、
BOM を落とすとスクリプト内の日本語が壊れて構文エラーになります(`tests/test_tts.py` で確認しています)。
